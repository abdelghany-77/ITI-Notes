Topic 24: DB2 Backup & Recovery Architecture

1. High-Level Concept & Architecture

In enterprise database administration, planning for system failures is not optional. A robust recovery strategy centers around two core business SLAs:

Recovery Time Objective (RTO)

The maximum acceptable duration of database downtime after a disaster before service is restored (e.g., "The database must be online within 15 minutes of a storage failure").

Recovery Point Objective (RPO)

The maximum acceptable data loss measured in time (e.g., "In the event of a catastrophic site failure, we must not lose more than 5 minutes of transaction data").

Transactional Logging Architecture (Write-Ahead Logging)

IBM DB2 guarantees ACID compliance through a highly optimized Write-Ahead Logging (WAL) protocol. Before any data page is modified in the buffer pool and written to persistent storage, the transactional changes must be recorded sequentially in the Transaction Log Buffer (`LOGBUFSZ`) and subsequently flushed to physical log files on disk by the log writer Engine Dispatchable Unit (EDU) known as db2loggw.

This logging structure consists of the following components:

  • Active Logs: Log files containing records of active, uncommitted transactions, or committed transactions whose dirty database pages have not yet been flushed from the buffer pools to disk. These are required for crash recovery.
  • Archive Logs: Completed active logs that are no longer needed for crash recovery but are kept intact in an external storage vault. They are required to roll forward restored backup images.
  • Primary Logs (`LOGPRIMARY`): Statically allocated log files pre-created when the database is activated. This prevents runtime delay overhead during transaction spikes.
  • Secondary Logs (`LOGSECOND`): Dynamic, on-demand log files created by the database manager only if the primary logs become completely full due to massive transactional volume.
Circular Logging (Default)

In this mode, DB2 overwrites old, committed log files sequentially in a ring buffer. Once the transactions in a log file are committed and their associated dirty data pages are flushed to disk, the log file is marked reusable.

Limitations: Restricts the database to crash recovery (automatic rollback of uncommitted work on startup) and **offline-only backups**. You cannot roll forward transactions.

Archive Logging (Log Retention)

Activated by setting the database configuration parameter LOGARCHMETH1 to a safe archival destination (e.g., local disk folder, tape drive, or Tivoli Storage Manager). Once a primary log file becomes full, DB2 marks it for archiving and spawns background writer threads to copy it to the secure archive location while continuing to write to other active logs.

Benefits: Enables **live online hot backups**, online tablespace-level backups, and Point-In-Time (PIT) rollforward recovery.

Backup Classification and Mechanics

  • Offline Backup: Requires exclusive database access. No applications can connect, and all active connections must be forced off. The database is frozen, and its exact storage files are copied.
  • Online Backup: Executed live while client transactions read and write to the tables. It captures a snapshot of the data pages while writing concurrent changes into the backup image's log stream to guarantee consistency upon restore. Requires archive logging to be active.
  • Full Backup: A complete baseline copy of all used data pages within the database.
  • Incremental Backup (Cumulative): A smaller backup containing only the data pages that have been modified since the last successful full backup.
  • Incremental Delta Backup (Non-Cumulative): An even smaller backup containing only the data pages that have been modified since the last successful backup of any type (full, incremental, or delta).

2. Full Syntax & CLP Commands

To control database recoverability, DBAs update parameters inside the Database Configuration (`DB CFG`) file using the Command Line Processor (CLP).

DB2 CLP - Sizing Recovery Logs
# 1. Update the number of statically pre-allocated primary logs
db2 "UPDATE DATABASE CONFIGURATION FOR ITIDB USING LOGPRIMARY 20"

# 2. Update the number of dynamic secondary logs
db2 "UPDATE DATABASE CONFIGURATION FOR ITIDB USING LOGSECOND 10"

# 3. Update the size of each log file (specified in 4KB pages; 8192 * 4KB = 32MB per log file)
db2 "UPDATE DATABASE CONFIGURATION FOR ITIDB USING LOGFILSIZ 8192"

# 4. Check the updated log configuration parameters
db2 "GET DATABASE CONFIGURATION FOR ITIDB" | grep -E "LOGPRIMARY|LOGSECOND|LOGFILSIZ"
DB2 CLP - Enabling & Disabling Archive Logging
# 1. Activate Archive Logging by pointing LOGARCHMETH1 to a secure disk folder
db2 "UPDATE DATABASE CONFIGURATION FOR ITIDB USING LOGARCHMETH1 DISK:/db2/archive_logs"

# Note: When enabling archive logging, the database enters a "backup pending" state.
# You MUST execute a full offline backup to establish a recovery baseline.
db2 "BACKUP DATABASE ITIDB TO /db2/backups"

# 2. Deactivate Archive Logging (Revert to Circular Logging)
db2 "UPDATE DATABASE CONFIGURATION FOR ITIDB USING LOGARCHMETH1 OFF"

# 3. Check logging status and paths
db2 "GET DATABASE CONFIGURATION FOR ITIDB" | grep -i logarch

3. Industry-Standard Lab: High-Transaction Retail Banking System

Scenario: Apex Banking Corp runs a core retail banking database (`APEXBANK`) that processes a peak of 8,000 transactions per second (TPS). The security policy mandates an **RPO of 0 (no committed data loss)** and an **RTO of less than 30 minutes**.

As the Lead DBA, you must size the active log files to handle dynamic workloads without causing application wait-states, configure archive logging, and verify the physical directories.

Active Log Sizing Math & Calculation

  • Average transaction size in logs = **4 KB** (1 page).
  • Peak Workload = **8,000 transactions/sec** = **32 MB of log data per second**.
  • We want active logs to hold at least **15 minutes** of concurrent uncommitted transaction history to prevent system stalls during massive batch processing:
    32 MB/sec × 900 seconds = 28,800 MB (approx 28.8 GB) of active log space required.
  • We select:
    LOGFILSIZ = 65536 (65536 × 4KB = 256MB per log file).
    LOGPRIMARY = 100 (100 × 256MB = 25.6GB primary active space).
    LOGSECOND = 20 (20 × 256MB = 5.12GB dynamic buffer space).
    Total Active Log Space capacity = **30.72 GB**.
DB2 CLP - Sizing and Activation Commands
# Ensure directories exist with proper system permissions
mkdir -p /db2/active_logs /db2/archive_logs /db2/backups
chown -R db2inst1:db2iadm1 /db2/active_logs /db2/archive_logs /db2/backups

# Connect to the database
db2 "CONNECT TO APEXBANK"

# Configure the optimized log sizing parameters
db2 "UPDATE DB CFG FOR APEXBANK USING LOGPRIMARY 100"
db2 "UPDATE DB CFG FOR APEXBANK USING LOGSECOND 20"
db2 "UPDATE DB CFG FOR APEXBANK USING LOGFILSIZ 65536"

# Relocate active logs to a dedicated high-speed SSD volume to prevent IO bottleneck
db2 "UPDATE DB CFG FOR APEXBANK USING NEWLOGPATH /db2/active_logs"

# Enable Archive Logging
db2 "UPDATE DB CFG FOR APEXBANK USING LOGARCHMETH1 DISK:/db2/archive_logs"

# Terminate connections to apply configuration changes
db2 "TERMINATE"
db2 "DEACTIVATE DATABASE APEXBANK"

# Database is now in Backup Pending. We must execute a baseline offline backup.
db2 "BACKUP DATABASE APEXBANK TO /db2/backups"

4. DBA Best Practices & Troubleshooting

Log Buffer Tuning (`LOGBUFSZ`)

The LOGBUFSZ parameter specifies the size of the database shared memory buffer allocated to hold transaction log records before flushing them to disk.

Best Practice: Set LOGBUFSZ to at least **4096 pages (16MB)** for high-transaction environments. This prevents the log buffer from filling up completely and forcing the application agents to block, waiting for synchronous disk I/O.

Dedicated Storage Isolation

Never place **Active Logs**, **Archive Logs**, and **Data Tablespaces** on the same physical disk array. A single drive failure could wipe out both the data and the logs, violating RPO/RTO mandates. Use RAID 10 SSD arrays for active logs to maximize sequential write throughput.

Troubleshooting Common Error: Active Log Space Full (SQL0964C)

Root Cause: All primary and secondary active log files are full. This occurs when:

  • An application executes massive data changes (e.g., deleting 10 million rows) in a single transaction without running COMMIT.
  • A connection hangs while holding an active transaction open, preventing DB2 from reusing completed log files.

DB2 Diagnostic Log Entry (`db2diag.log`):

DBA Remedy Protocol:

  1. Locate the rogue application holding the oldest uncommitted transaction: 
    db2 "SELECT APPLICATION_HANDLE, UOW_START_TIME, UOW_LOG_SPACE_USED, AUTHID FROM SYSIBMADM.LOG_UTILIZATION ORDER BY UOW_LOG_SPACE_USED DESC"

    db2 "FORCE APPLICATION (4217)"
  3. Dynamically increase the secondary log buffer capacity to buy time for the rollback to complete without shutting down the database manager: 
    db2 "UPDATE DB CFG FOR APEXBANK USING LOGSECOND 40"

Topic 25: DB2 Database Backup Operations

1. High-Level Concept & Architecture

Executing backup operations in a high-concurrency production database requires deep knowledge of how DB2 reads data and writes backup streams without impacting operational response times.

The Internals of DB2 Online Backup

When an ONLINE backup is initiated, DB2 does not lock the tables. Instead, it reads the data pages sequentially. If an application updates a record on a page that has already been backed up, or is currently being read, DB2 allows it.

To handle this data drift, the backup utility tracks the starting **Log Sequence Number (LSN)** and ending **LSN** of the backup process. When the backup finishes, the utility extracts all active transaction log files that were generated during the backup execution and bundles them directly inside the backup image using the INCLUDE LOGS clause. This ensures that when the backup is restored, it can be immediately rolled forward to a transactionally consistent state.

Tablespace-Level Backups

Rather than backing up an entire multi-terabyte database, DB2 allows you to target individual tablespaces (e.g., USERSPACE1).

Use Case: Back up active transaction tablespaces daily while backing up static history or read-only reporting tablespaces weekly. This dramatically reduces the backup window and disk space.

The `TRACKMOD` Change Tracking Engine

Incremental and delta backups rely on the **Track Modified Pages (`TRACKMOD`)** database configuration parameter.

When TRACKMOD is set to ON, DB2 reserves a special bit flag in the header of each page. Any transaction that modifies a page sets this flag. The backup utility then simply scans the page headers and copies only the flagged pages, avoiding full-table scans.

2. Full Syntax & CLP Commands

Here is the syntax used by DBAs to configure change tracking, compress backups, and run online, offline, incremental, and tablespace backups.

# 2. Restart the database to activate TRACKMOD
db2 "FORCE APPLICATION ALL"

db2 "BACKUP DATABASE ITIDB TABLESPACE (USERSPACE1, SYSCATSPACE) ONLINE TO /db2/backups INCLUDE LOGS"

4. DBA Best Practices & Troubleshooting

Backup Performance Tuning Parameters

To prevent the backup utility from hogging all system CPU and I/O resources, or to speed up huge backups, use tuning parameters:

  • `PARALLELISM n`: Spawns n thread readers to read tablespaces in parallel. Set n equal to the number of physical CPU cores allocated.
  • `WITH num-buffers BUFFERS`: Allocates memory buffers. Ideal for preventing I/O stalls.
  • `BUFFER size`: Sets the size of the backup buffers (specified in 4KB pages). Set this parameter to be a multiple of the tablespace extent size.
Tuned Online Backup
db2 "BACKUP DATABASE STOREDB ONLINE TO /db2/backups WITH 4 BUFFERS BUFFER 2048 PARALLELISM 4 INCLUDE LOGS"

Troubleshooting Common Backup Errors

  • SQL2426N ("The incremental backup failed because tracking is not enabled")
    Root Cause: An incremental or delta backup was requested, but TRACKMOD is set to OFF.
    Remedy: Run: 
    db2 "UPDATE DB CFG FOR STOREDB USING TRACKMOD ON"
db2 "DEACTIVATE DATABASE STOREDB"
db2 "BACKUP DATABASE STOREDB TO /db2/backups" # establish baseline
  • SQL1035N ("The database is currently in use")
    Root Cause: An offline backup was executed, but active users or application connections are currently connected to the database.
    Remedy: Force off connections and deactivate: 
    db2 "FORCE APPLICATION ALL"
db2 "DEACTIVATE DATABASE STOREDB"
db2 "BACKUP DATABASE STOREDB TO /db2/backups"
  • Backup Storage Cleanup & Pruning:
    Disk space will exhaust if backup files are never deleted. Use the PRUNE HISTORY command to clean up: 
    db2 "PRUNE HISTORY 20260522 AND DELETE" # Deletes history records and physical backup files older than May 22, 2026

Topic 26: DB2 Database Restore & Reconstruction

1. High-Level Concept & Architecture

When hardware fails or corruption occurs, the DBA must perform a restoration. Understanding the database restore engine's internal execution model is critical for minimizing system downtime.

Database Restore Engine Internals

When the RESTORE command is executed, DB2 performs the following background tasks:

  1. Reads the backup image header, extracting database properties, collating codeset rules, and tablespace metadata structure definitions.
  2. Checks if the target database exists. If it does not, DB2 auto-creates the physical shell database with matching configuration parameters.
  3. Allocates system memory buffers and reads data page chunks from the backup stream.
  4. Verifies and recreates physical tablespace containers (directories or raw partitions) on the target disk.
  5. Writes the data pages into their respective container files.
  6. If requested, extracts archived log files embedded inside the backup image and places them in a target folder.
Redirected Restore Architecture

If the physical disk array containing the tablespace containers fails, or if you are migrating the database to a new server, the restore will fail because the target directories do not exist or are corrupted.

Solution: A **Redirected Restore**. This process allows you to intercept the restore stream, change the physical paths of database tablespace containers, and then resume writing data pages to the new storage paths.

Online Tablespace Restore

If a single physical drive hosting transaction tablespace containers fails, DB2 does not require you to restore the entire database. You can perform an **Online Tablespace Restore** on the affected tablespace while all other database tablespaces remain online and accessible to applications.

2. Full Syntax & CLP Commands

These are the fundamental commands used to execute standard restores, extract recovery logs, and run multi-step redirected container restores.

DB2 CLP - Standard Restore Commands
# 1. Simple restore from backup directory
db2 "RESTORE DATABASE ITIDB FROM /db2/backups TAKEN AT 20260522131000"

# 2. Restore database and extract embedded active logs into a specific recovery directory
db2 "RESTORE DATABASE ITIDB FROM /db2/backups TAKEN AT 20260522131000 LOGTARGET /db2/extracted_logs"

# 3. Restore a single specific tablespace (e.g. USERSPACE1) while database is online
db2 "RESTORE DATABASE ITIDB TABLESPACE (USERSPACE1) ONLINE FROM /db2/backups TAKEN AT 20260522131000"
DB2 CLP - Redirected Restore Flow
# Step 1: Initiate Redirected Restore (Database goes into RESTORE_PENDING state)
db2 "RESTORE DATABASE ITIDB FROM /db2/backups TAKEN AT 20260522131000 REDIRECT"

# Step 2: Redefine storage paths for affected tablespaces
# Format: SET TABLESPACE CONTAINERS FOR <tablespace_id> USING (PATH '<new_path>')
db2 "SET TABLESPACE CONTAINERS FOR 3 USING (PATH '/safe_disk/userspace1')"

# Step 3: Command DB2 to compile changes and complete the restoration
db2 "RESTORE DATABASE ITIDB CONTINUE"

3. Industry-Standard Lab: Disaster Recovery Redirected Restore

Scenario: "Capital Trust" database server (`TRUSTDB`) suffered a catastrophic disk array crash on volume /dbdata/old_storage, destroying the containers of the system catalog space (`SYSCATSPACE` ID 0) and the primary user tablespace (`USERSPACE1` ID 3).

As the DBA on duty, you have swapped the broken array with new storage mounted at /safe_storage. You must perform a **Redirected Restore** to rebuild the database container structures and verify the restoration.

# Step 1: Start the redirected restore sequence
db2 "RESTORE DATABASE TRUSTDB FROM /db2/backups TAKEN AT 20260522131000 REDIRECT"

# Step 2: Query the tablespace IDs and physical containers defined in the backup image
db2 "LIST TABLESPACE CONTAINERS FOR TRUSTDB"

# Step 3: Re-map containers for SYSCATSPACE (Tablespace ID 0)
db2 "SET TABLESPACE CONTAINERS FOR 0 USING (PATH '/safe_storage/syscat')"

# Step 4: Re-map containers for USERSPACE1 (Tablespace ID 3)
db2 "SET TABLESPACE CONTAINERS FOR 3 USING (PATH '/safe_storage/user1')"

# Step 5: Execute the continue restore command to commit the container mapping changes
db2 "RESTORE DATABASE TRUSTDB CONTINUE"

4. DBA Best Practices & Troubleshooting

Redirected Restore Automation Scripting

For complex production databases containing dozens of tablespaces and containers, writing container redirection commands manually during a high-pressure disaster recovery incident is error-prone.

Best Practice: Always generate a pre-configured redirected restore script from the backup image itself using the REDIRECT GENERATE SCRIPT clause:

Generate Recovery Script
db2 "RESTORE DATABASE TRUSTDB FROM /db2/backups TAKEN AT 20260522131000 REDIRECT GENERATE SCRIPT recover_trustdb.clp"

This generates a fully formatted shell script `recover_trustdb.clp` containing all required SET TABLESPACE CONTAINERS command templates, which you can simply edit and execute.

Troubleshooting Common Restore Errors

  • SQL2539W ("The database already exists. Overwrite? (y/n)")
    Root Cause: A safety warning indicating you are attempting to restore a database over an existing active database instance of the same name.
    Remedy: Add the REPLACE keyword to the command or enter y in interactive terminals: 
    db2 "RESTORE DATABASE TRUSTDB FROM /db2/backups TAKEN AT 20260522131000 REPLACE"
  • SQL2519N ("Restore failed because database configuration is incompatible")
    Root Cause: An attempt was made to restore a backup taken on a different DB2 version or platform (e.g., restoring database from DB2 V11.5 onto a server running DB2 V10.5).
    Remedy: DB2 does not support restoring backups to older database engine versions. Upgrade the target engine to be equal to or higher than the backup source's version.

Topic 27: DB2 Rollforward Recovery & Point-In-Time Recovery

1. High-Level Concept & Architecture

Restoring a database backup is only the first step in disaster recovery. A restored backup image only represents the state of the database at the precise moment the backup was taken. Any transactions executed after the backup timestamp are missing.

The Rollforward Recovery Engine

To restore data up to the point of failure, DB2 utilizes the **Rollforward Recovery Engine**. This engine reads sequential archived transaction logs and reapplies all committed changes to the restored data pages.

This execution process runs in two distinct phases:

  1. REDO Phase: The engine scans the transaction log sequence starting from the backup checkpoint LSN. It reapplies all transaction records (inserts, updates, deletes, DDL changes) to the database pages, bringing the database up to the point of failure.
  2. UNDO Phase: Once the target recovery boundary is reached, the engine scans backward to identify any transactions that were active (in-flight) but uncommitted at that boundary. It rolls back these uncommitted transactions to guarantee transactional integrity.
The ROLL-FORWARD PENDING State

After a database is restored, DB2 places it in the ROLL-FORWARD PENDING state.

This is an essential database protection mechanism. While in this state, the database is locked. No users, scripts, or application connections can read or write to it. This prevents access to transactionally inconsistent tables before the log records are fully applied.

Point-In-Time (PIT) Recovery

While a standard rollforward applies all logs to the **end of logs** (complete recovery), a **Point-In-Time (PIT) Recovery** stops the rollforward process at a specific date and timestamp.

Use Case: If a developer accidentally executes a rogue DDL statement (e.g., truncating an active customer ledger table) at 14:05:12, the DBA can restore the database and roll forward to 14:05:10, stopping right before the corruption occurred.

2. Full Syntax & CLP Commands

These commands are used to check recovery status, roll forward to the end of logs, execute PIT recovery, and use overflow log paths.

DB2 CLP - Checking & Completing Rollforward
# 1. Query the database's current rollforward state and required log sequence
db2 "ROLLFORWARD DATABASE ITIDB QUERY STATUS"

# 2. Roll forward all transactions to the end of logs and put the database back online
db2 "ROLLFORWARD DATABASE ITIDB TO END OF LOGS AND STOP"

# 3. Roll forward database utilizing a separate overflow log path
# (Used when log files are stored in a safe backup folder rather than active log path)
db2 "ROLLFORWARD DATABASE ITIDB TO END OF LOGS AND STOP OVERFLOW LOG PATH (/db2/extracted_logs)"

# 4. Roll forward a specific tablespace only
db2 "ROLLFORWARD DATABASE ITIDB TO END OF LOGS AND STOP TABLESPACE (USERSPACE1)"
DB2 CLP - Point-In-Time Recovery Syntax
# Roll forward to specific timestamp using ISO format
# Format: YYYY-MM-DD-HH.MM.SS.UUUUUU (Year-Month-Day-Hour.Minute.Second.Microseconds)
db2 "ROLLFORWARD DATABASE ITIDB TO 2026-05-22-14.05.10.000000 USING LOCAL TIME AND STOP"

# Note: If you start a rollforward and realize you typed the timestamp wrong, 
# you can cancel the current run and start over:
db2 "ROLLFORWARD DATABASE ITIDB CANCEL"

4. DBA Best Practices & Troubleshooting

Complete recovery vs. PIT

Always use TO END OF LOGS for hardware failure recovery. Only use Point-In-Time (PIT) recovery for logical failures (accidental deletes, truncations, or application bugs).

Warning: Performing a PIT recovery creates a new database log sequence fork. Any transaction logs created after the PIT timestamp on the original timeline are orphaned and cannot be applied in future recovery runs.

Overflow Log Path Configuration

When rolling forward, DB2 looks for logs in the default active log directory. If you are recovering onto a backup server where those active logs do not exist, use the OVERFLOW LOG PATH parameter to point directly to the folder containing your extracted archived log files.

Troubleshooting Common Recovery Errors

  • Database Stuck in ROLL-FORWARD PENDING State
    Root Cause: A restore command completed, or a rollforward was run without the STOP or AND STOP keyword. The engine remains open, expecting additional logs to be supplied.
    Remedy: Execute the stop command directly to take the database out of pending state: 
    db2 "ROLLFORWARD DATABASE TRADE_DB STOP"
  • SQL1273N ("Logical end of database logs was reached, missing log sequence")
    Root Cause: A required log file is missing from the active log path or archive directory during the rollforward process. The recovery engine cannot proceed because there is a gap in the log sequence.
    Remedy: Check the db2diag.log to identify the missing log file name (e.g., `S0000105.LOG`). Locate it inside your backup vault or archive drive, copy it to the database log path, and re-run the rollforward.

`TO END OF LOGS AND STOP` All active & archive logs Applies all transactions up to the last committed write on disk. Brings database online (ready for connections) None. Standard recovery path.
`TO <timestamp> AND STOP` Logs up to target time Applies changes up to the specified second, then rolls back in-flight transactions. Brings database online (ready for connections) High. Orphans subsequent logs; cannot undo this action after stopping.
