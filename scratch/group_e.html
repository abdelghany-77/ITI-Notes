Group E Overview: High-Performance Data Utilities & Disaster Recovery

Introduction to Group E Content

In high-transaction enterprise databases, managing data movement safely and maintaining absolute system availability during disasters are the two primary pillars of a Senior DB2 DBA's role. This guide provides deep academic and practical training on two major sub-fields of DB2 LUW (Linux, UNIX, and Windows) administration:

  • Data Ingestion & Movement (Topics 32 & 33): Detailed architectural analysis of standard utilities (EXPORT, IMPORT) versus high-performance direct page write mechanics (LOAD), focusing on resource usage, logging bypasses, and recovery state management.
  • IBM DB2 Fundamentals Certification (Topic 34): Exam preparation and detailed review of core DBA syllabus concepts including privileges, authorities (SYSADM, SECADM, DBADM), and isolation levels (UR, CS, RS, RR).
  • High Availability Disaster Recovery (Topics 35 & 36): Architectural foundations and execution parameters for DB2 HADR replication. Focuses on the four synchronization modes (SYNC, NEARSYNC, ASYNC, SUPERASYNC), planned role reversals, and simulated catastrophic takeover drills.

Topic 32: Data Movement Utilities (EXPORT and IMPORT)

1. High-Level Concept & Architecture

Database administrators often need to move data between databases, migrate schemas, or interface with external systems (such as BI tools, spreadsheets, or third-party databases). IBM DB2 provides the standard EXPORT and IMPORT utilities as SQL-driven interfaces to handle these requirements.

The EXPORT Process Model

EXPORT reads data from database tables by compiling and executing a standard SQL SELECT statement. The retrieved data rows are formatted and written to an external operating system file.

  • Locking: EXPORT acquires an Intent Share (IS) lock on the source table, allowing concurrent users to perform SELECT, INSERT, UPDATE, and DELETE operations.
  • Consistency: The DBA can configure isolation levels (such as UR or CS) inside the export call to control dirty reads.
The IMPORT Process Model

IMPORT parses data rows from an external operating system file and inserts them row-by-row into the target DB2 table using native SQL INSERT statements under the hood.

  • Logging: Every inserted row generates standard transactional log records, making IMPORT fully recoverable.
  • Enforcement: Since it uses standard INSERT statements, IMPORT evaluates and enforces all table constraints, unique indexes, and triggers automatically.
  • Locking: IMPORT acquires Row Exclusive (NX) locks, which can escalate to Table Exclusive (X) locks during bulk transfers.

Supported File Formats

  • DEL (Delimited ASCII): A standard text format where columns are separated by delimiters (e.g., commas or tabs) and character strings are optionally wrapped in double quotes. Extremely portable for exchanges with tools like Microsoft Excel or PostgreSQL.
  • IXF (Integration Exchange Format): IBM's proprietary binary format. It stores not only the raw data but also the complete schema metadata (column names, exact data types, constraints, and indexes). It is the premier format for DB2-to-DB2 database migrations because it can reconstruct a dropped table automatically.
  • ASC (Non-delimited ASCII): A fixed-width text format where fields are defined by precise start and end position offsets. Common when importing legacy mainframe or COBOL-generated flat files.
  • WSF (Worksheet Format): Legacy spreadsheet format (such as Lotus 1-2-3 or older Excel formats). Rarely used in modern environments but still supported.

2. Full Syntax & CLP Commands

Both EXPORT and IMPORT are executed directly via the DB2 Command Line Processor (CLP). The syntax supports a wide range of file modifiers to handle formatting variations.

DB2 EXPORT CLP Syntax
db2 "EXPORT TO <filename> OF <format> \
     [LOBS TO <lob_path> LOBFILE <lob_filename>] \
     [MODIFIED BY <modifiers>] \
     SELECT <columns> FROM <tables> [WHERE <conditions>]"
DB2 IMPORT CLP Syntax
db2 "IMPORT FROM <filename> OF <format> \
     [COMMITCOUNT <n>] \
     [MODIFIED BY <modifiers>] \
     [INSERT | INSERT_UPDATE | REPLACE | CREATE | REPLACE_CREATE] \
     INTO <target_table> [(<columns>)]"

Core Modifiers & Modes Explained

  • Import Modes:
    • INSERT: Appends the imported rows to the existing target table data.
    • INSERT_UPDATE: Appends new rows and updates existing rows that have matching primary keys (requires a primary key on the target table).
    • REPLACE: Deletes all existing rows from the target table (clearing it completely) and then inserts the new rows.
    • CREATE: Creates a new table based on the metadata in the IXF file, then inserts the data (only works with IXF files).
    • REPLACE_CREATE: If the target table exists, acts like REPLACE. If it does not exist, creates the table using the IXF metadata and inserts the rows.
  • Common File Modifiers:
    • coldel;: Overrides the default column delimiter (e.g., modified by coldel| uses a pipe symbol).
    • chardel"": Overrides the character string delimiter.
    • identityignore: Tells the engine to ignore values in the import file for an identity column, allowing DB2 to auto-generate sequence numbers.
    • identityoverride: Tells the engine to force insertion of the exact identity column values present in the import file.

3. Industry-Standard Practical Lab: Retail Analytics Ingestion

Scenario: The DBA needs to migrate employee tables from a legacy branch database into the central analytical database. We will export data as a Delimited ASCII (DEL) file and then import it into the central system, overriding automatic identity sequences.

Step 1: Create the Source Table & Insert Seed Data
-- Connect to source branch database
db2 "CONNECT TO BRANCHDB"

-- Create source employee table with an identity column
db2 "CREATE TABLE BranchEmployees ( \
     EmpID INT GENERATED ALWAYS AS IDENTITY (START WITH 100 INCREMENT BY 1), \
     EmpName VARCHAR(50) NOT NULL, \
     HireDate DATE NOT NULL, \
     Salary DECIMAL(10,2) NOT NULL \
     )"

-- Insert test seed records
db2 "INSERT INTO BranchEmployees (EmpName, HireDate, Salary) VALUES ('Ahmed Ali', '2021-05-15', 7500.00)"
db2 "INSERT INTO BranchEmployees (EmpName, HireDate, Salary) VALUES ('Sarah John', '2023-01-10', 9200.00)"
db2 "INSERT INTO BranchEmployees (EmpName, HireDate, Salary) VALUES ('Mostafa Omar', '2024-03-22', 6800.00)"
Step 2: Export Data to a Delimited Text File
-- Export the data to a delimited file using a pipe delimiter
db2 "EXPORT TO '/dbdata/exports/emp_migration.del' OF DEL \
     MODIFIED BY coldel| \
     SELECT EmpID, EmpName, HireDate, Salary FROM BranchEmployees"

Technical Walkthrough: Behind the Scenes

  1. Connection and Parser: The DBA fires the EXPORT command. The connection agent (db2agent) parses the SQL query and requests metadata details.
  2. Buffer and File Write: DB2 reads rows into Database Shared Memory (buffer pool). The export engine writes these rows to the local filesystem (emp_migration.del) using the specified delimiter (|).
  3. Target Lock Acquisition: During IMPORT, the db2agent issues individual INSERT statements. It acquires Intent Share (IS) locks on the tablespace and Row Exclusive (NX) locks on target rows.
  4. Identity Overriding: Because the identityoverride modifier is set, the DB2 engine disables internal sequence generators and directly writes the values (100, 101, 102) into the target identity column.
  5. Log Buffer Write: Each insert generates standard transactional recovery logs. A transaction commit is issued at the end, writing logs to disk.

4. DBA Best Practices & Troubleshooting

Common Import Pitfall: Transaction Log Full

Diagnostic Code: SQL0964C The transaction log for the database is full.

Root Cause: During large imports (hundreds of thousands of rows), the utility performs one long continuous transaction. If the total size of inserted records exceeds the available active transaction logs (defined by LOGFILSIZ, LOGPRIMARY, and LOGSECOND in the DB CFG), the database runs out of active log space and rollbacks the entire import.

Remedy: Always specify the COMMITCOUNT parameter when importing large datasets. This forces DB2 to commit transactions and release log space periodically:

db2 "IMPORT FROM data.del OF DEL COMMITCOUNT 10000 INSERT INTO target_table"

Common Error: Character Code Page Mismatches

Diagnostic Code: SQL0332N Character conversion from the source code page "1252" to the target code page "1208" is not supported.

Root Cause: The operating system console environment has a different code page setting than the target database (e.g., importing Windows-1252 characters into a UTF-8 Unicode database).

Remedy: Prior to starting the import, force the DB2 application client environment to align with the target database's code page using the system environment variables:

# On Windows (cmd/PowerShell):
set DB2CODEPAGE=1208

# On Linux/UNIX:
export DB2CODEPAGE=1208
db2 terminate

DBA Best Practices for Data Movement

  • Table Reconstruction: When moving database structures between different DB2 environments, always prefer the IXF format. It contains the exact schema definition, eliminating manual DDL creations.
  • Lock Escalation Management: Sizable imports can trigger lock escalation, locking out concurrent operations. Monitor this using db2pd -db CENTRALDB -locks. To minimize lock footprints, increase the database parameters LOCKLIST and MAXLOCKS.
  • Delimiters: When exporting text columns that may contain commas or quotes (e.g., comments, addresses), use a rare character as your column delimiter (e.g., modified by coldel; or coldel|) to avoid parsing failures.

Topic 33: High-Performance Data Ingestion (The LOAD Utility)

1. High-Level Concept & Architecture

When ingesting massive datasets (e.g., millions of transactional rows in a data warehouse), the standard IMPORT utility is often too slow because of its row-by-row SQL processing, index updating, and transaction logging overhead. DB2 provides the highly optimized LOAD utility to solve this bottleneck.

The LOAD Ingestion Paradigm

Instead of issuing individual SQL INSERT statements, the LOAD utility bypasses the entire database engine's query processor and SQL engine. It parses input data, formats it into binary database data pages in memory, and writes these pages directly onto physical disk tablespace containers.

Because it bypasses the SQL layer, referential integrity check engines, triggers, and—most importantly—transaction logging, LOAD runs 10 to 50 times faster than IMPORT.

The Four Operational Phases of LOAD
  1. 1. LOAD Phase: Reads input records, converts the data to internal DB2 storage format, and writes formatted pages directly to the database containers. Simultaneously, it extracts index keys and writes them to a dedicated sorting area in memory.
  2. 2. BUILD Phase: Reads the sorted index keys from the sort buffer and rebuilds all indexes defined on the target table in a highly optimized linear sweep.
  3. 3. DELETE Phase: If unique indexes or constraints are defined, LOAD scans for duplicate rows, deletes violating records from the table, and logs the deleted rows to a user-defined Exception Table.
  4. 4. INDEXING Phase: The final evaluation phase where the system ensures all indexes are physically consistent and ready for queries.
Logging Bypass & Database Recoverability

Because LOAD bypasses transaction logging to achieve maximum performance, DB2 needs to protect the database against media failures. If a crash occurs and archive logging is enabled, a standard LOAD leaves the target tablespace in a Backup Pending state (non-accessible).

DBAs manage this recovery requirement using two options:

  • COPY YES: Writes a physical backup copy of the loaded data blocks to a designated location (e.g., a backup directory or Tivoli Storage Manager) during the load, keeping the tablespace fully accessible.
  • NONRECOVERABLE: Avoids the Backup Pending state without generating a copy. However, if you later perform a roll-forward database recovery, the table is marked as unusable and must be dropped and recreated.

2. Full Syntax & CLP Commands

The LOAD command supports options for error routing, recoverability settings, and load lifecycle management.

DB2 LOAD CLP Command Syntax
db2 "LOAD FROM <filename> OF <format> \
     [METHOD P (<col_offsets>)] \
     [MODIFIED BY <modifiers>] \
     [INSERT | REPLACE | RESTART | TERMINATE] \
     INTO <target_table> \
     [FOR EXCEPTION <exception_table>] \
     [COPY YES TO <backup_directory> | NONRECOVERABLE]"

Administrative Parameter Definitions

  • INSERT / REPLACE: Standard operations to either append data or replace all existing data in the table.
  • RESTART: If a load fails midway (e.g., due to a disk space exhaustion), fixing the resource and running LOAD ... RESTART automatically resumes processing from the last internal commit checkpoint.
  • TERMINATE: Rolls back the failed load, cleans up all temporary files, and removes the tablespace from its locked state.
  • FOR EXCEPTION: Specifies an existing database table where the utility will route any records that violate unique or primary key constraints.

3. Industry-Standard Practical Lab: Retail Analytics Ingestion

Scenario: The DBA must load 1 million new transaction records into a data warehouse table (TransactionStore). To maintain recoverability without placing the tablespace in backup pending, the DBA configures the load with COPY YES and sets up an exception table to capture duplicate records.

Step 1: Set Up Tables & Exception Capture
-- Connect to Data Warehouse Database
db2 "CONNECT TO DWDB"

-- Create main transaction store table
db2 "CREATE TABLE TransactionStore ( \
     TxID BIGINT NOT NULL PRIMARY KEY, \
     StoreCode VARCHAR(10) NOT NULL, \
     TxAmount DECIMAL(10,2) NOT NULL, \
     TxTimestamp TIMESTAMP NOT NULL \
     )"

-- Create an Exception Table matching the schema of TransactionStore,
-- plus two specialized columns required by DB2 to log violations.
db2 "CREATE TABLE TransactionExceptions ( \
     TxID BIGINT, \
     StoreCode VARCHAR(10), \
     TxAmount DECIMAL(10,2), \
     TxTimestamp TIMESTAMP, \
     TimestampCol TIMESTAMP, \
     MsgCol CLOB(32K) \
     )"
Step 2: Execute the High-Speed Load Utility
-- Execute bulk load using COPY YES to keep the tablespace active
db2 "LOAD FROM '/dbdata/raw/tx_may2026.del' OF DEL \
     MODIFIED BY coldel, \
     REPLACE INTO TransactionStore \
     FOR EXCEPTION TransactionExceptions \
     COPY YES TO '/dbdata/backups/load_copies'"

Technical Walkthrough: Behind the Scenes

  1. Utility Heap Allocation: DB2 allocates memory from the utility heap (sized by UTIL_HEAP_SZ) to hold internal parsing and processing buffers.
  2. Thread Dispatching: The engine spawns parallel EDUs (Load Readers, Formatters, Writers) to maximize CPU core utilization.
  3. Direct Block Writing (LOAD Phase): Formatters build DB2 pages in memory. Writers write these pages directly to the tablespace containers. No SQL statements are compiled or executed.
  4. Index Rebuilding (BUILD Phase): All index keys are extracted and sorted in memory (using SORTHEAP), then written to the index tablespace block.
  5. Duplicate Removal (DELETE Phase): Unique key violations are located, deleted, and routed to the TransactionExceptions table.
  6. Backup Generation (COPY YES): Simultaneously, physical page blocks are copied to /dbdata/backups/load_copies, keeping the tablespace fully accessible to applications.

4. DBA Best Practices & Troubleshooting

Understanding and Clearing LOAD PENDING State

Diagnostic Warning: SQL3500W The table "DB2INST1.TRANSACTIONSTORE" is in "Load Pending" state.

Root Cause: If a LOAD utility run is interrupted midway (due to a power failure, transaction rollback, disk exhaustion, or manual termination), the DB2 engine locks the target table. The table enters LOAD PENDING state, blocking all read and write queries to protect data integrity.

Remedy: To clear this state, the DBA must perform one of two actions:

  1. Option A: Abort and Rollback (Restore to initial state): 
    db2 "LOAD TERMINATE INTO TransactionStore"
  2. Option B: Resume and Complete (Continue from checkpoint):

    Fix the underlying issue (e.g., add disk space) and run:

    db2 "LOAD RESTART FROM '/dbdata/raw/tx_may2026.del' OF DEL INTO TransactionStore"

Tablespace Access Blocked (Backup Pending State)

Diagnostic Code: SQL0290N Table space access is not allowed. SQLSTATE=55039

Root Cause: The database is configured for archival logging, and a LOAD utility was run using default settings (COPY NO) without specifying the NONRECOVERABLE flag. To prevent potential restore inconsistencies, DB2 locks the tablespace, putting it into a Backup Pending state.

Remedy: Take a backup of the tablespace to make it accessible again:

db2 "BACKUP DATABASE DWDB TABLESPACE (USERSPACE1) ONLINE TO '/dbdata/backups'"

Performance Tuning Parameters for LOAD

  • Sizing the Utility Heap (UTIL_HEAP_SZ): Sizing this parameter appropriately is critical for bulk loads. Set this database configuration parameter to at least 50,000 pages for large loads: 
    db2 "UPDATE DATABASE CONFIGURATION FOR DWDB USING UTIL_HEAP_SZ 50000 AUTOMATIC"
  • Parallelism: Sizing CPU and Disk parallelism helps optimize throughput:
    • CPU_PARALLELISM: Number of processes/threads spawned to parse data. Defaults to the number of physical cores.
    • DISK_PARALLELISM: Sized according to the number of storage containers per tablespace.

Topic 34: DB2 9 Fundamentals Exam Review (Exam 730)

1. Exam Domains Overview

The IBM Certified Database Associate - DB2 9 Fundamentals Exam (Exam 730) validates a candidate's basic understanding of DB2 LUW database administration. Understanding these core concepts is highly relevant for both certification preparation and daily database operations.

Syllabus Domain Breakdown
  • Domain 1: Planning (18%): DB2 products, data structures, features, licensing models, and database creation.
  • Domain 2: Security (20%): Authentication, authorization, authorities (SYSADM, SECADM, etc.), database privileges, and security roles.
  • Domain 3: Database Objects (18%): Creating tables, indexes, views, schemas, and constraint configurations.
  • Domain 4: Working with Data (24%): Standard SQL commands, isolation levels, concurrency anomalies, and locking.
  • Domain 5: Tools & Utilities (20%): Operating the CLP, EXPORT, IMPORT, LOAD, RUNSTATS, and REORG utilities.
DB2 Security & Authority Architecture

A key focus of DB2 security is the strict separation of database access roles:

  • SYSADM (System Administrator): The highest instance-level authority. Can start/stop the instance, configure environments, and create databases, but has no default access to user table data in newer versions.
  • SECADM (Security Administrator): The highest database-level security authority. Manages security policies, grants database privileges, and configures auditing.
  • DBADM (Database Administrator): Manages database objects, configurations, and grants object privileges.

2. Key Technical Review: Isolation Levels & Concurrency

The exam heavily tests a candidate's understanding of **database isolation levels** and their ability to prevent concurrency anomalies.

The Three Concurrency Anomalies

  • Dirty Read: A transaction reads uncommitted data modifications made by another transaction. If the other transaction rolls back, the data read becomes invalid.
  • Non-repeatable Read: A transaction reads a row, and a concurrent transaction updates or deletes that row. If the first transaction re-reads the row, it receives different values.
  • Phantom Read: A transaction executes a query returning a set of rows matching a search criteria. A concurrent transaction inserts new matching rows. If the first transaction repeats the query, it receives a different set of rows.

DB2 Isolation Levels and Locking Behaviors

  • Uncommitted Read (UR - "Dirty Read"): Acquires almost no locks during read operations. Offers maximum concurrency but allows dirty reads, non-repeatable reads, and phantoms.
  • Cursor Stability (CS - "Default"): Acquires a lock on the row currently pointed to by the cursor. The lock is released as soon as the cursor moves to the next row. Prevents dirty reads.
  • Read Stability (RS): Locks all rows returned by the query until the transaction completes. Concurrent transactions cannot modify or delete these rows, but they can insert new records that match the query criteria (allowing phantom reads).
  • Repeatable Read (RR - "Serializable"): Locks the entire range of data queried, including any scanned pages. Prevents all concurrency anomalies (dirty reads, non-repeatable reads, and phantoms) but significantly limits database concurrency.

3. High-Fidelity Practice Questions (Certification Drill)

Q1: Which utility writes formatted pages directly to the tablespace containers, bypassing transaction logging?

Options:

  • A) IMPORT
  • B) EXPORT
  • C) LOAD
  • D) db2move

Correct Answer: C

Technical Rationale: The LOAD utility is designed to write formatted pages directly to the tablespace containers. It bypasses the SQL engine, constraint checks, triggers, and transaction logging, making it the highest-performance utility for bulk data ingestion.

Q2: An application developer needs to run a query that guarantees zero dirty reads while maintaining maximum concurrency. Which isolation level should be selected?

Options:

  • A) Repeatable Read (RR)
  • B) Read Stability (RS)
  • C) Cursor Stability (CS)
  • D) Uncommitted Read (UR)

Correct Answer: C

Technical Rationale: Cursor Stability (CS) is the default isolation level. It prevents dirty reads by acquiring a lock on the current row and releasing it as soon as the cursor moves, ensuring a good balance of data integrity and concurrency.

Q3: A DBA needs to transfer a table structure, along with its indexes and constraints, from a development environment to production. Which file format should be selected during export?

Options:

  • A) DEL
  • B) IXF
  • C) ASC
  • D) CSV

Correct Answer: B

Technical Rationale: IXF (Integration Exchange Format) is a binary format that stores both the table data and its schema metadata (columns, constraints, and indexes). It allows DB2 to automatically reconstruct the table during an import.

Q4: In DB2 security, which authority is required to configure database audit policies and grant security-related privileges?

Options:

  • A) SYSADM
  • B) DBADM
  • C) SECADM
  • D) SQLADM

Correct Answer: C

Technical Rationale: SECADM (Security Administrator) is the database-level authority responsible for managing security policies, roles, audit configurations, and granting security privileges. This role is strictly separated from data administration tasks.

Q5: A table is updated by Transaction A, but not yet committed. Transaction B attempts to read this table. Under which isolation level can Transaction B read Transaction A's uncommitted modifications?

Options:

  • A) Uncommitted Read (UR)
  • B) Cursor Stability (CS)
  • C) Read Stability (RS)
  • D) Repeatable Read (RR)

Correct Answer: A

Technical Rationale: Uncommitted Read (UR) allows read operations to proceed without acquiring row locks. This allows transactions to read uncommitted changes (dirty reads) made by other concurrent connections.

4. DBA Preparation Strategy

Tips for DB2 Fundamentals Exam Success

  • Understand Parameter Scopes: Always distinguish between instance-level settings (stored in the Database Manager Configuration - dbm cfg) and database-level settings (stored in the Database Configuration - db cfg).
  • Study CLI Utilities: Memorize the primary administrative command-line tools:
    • db2look: Generates the DDL statements for database objects.
    • db2move: Automates moving multiple tables between databases.
    • db2exfmt: Formats and displays query execution plans.
  • Analyze Locking Behaviors: Understand how lock escalations occur when the database-managed lock list (LOCKLIST) becomes full, and how to configure MAXLOCKS to prevent table locks.

Topic 35: HADR Standby Synchronization Modes (SYNC/NEARSYNC/ASYNC/SUPERASYNC)

1. High-Level Concept & Architecture

IBM DB2 High Availability Disaster Recovery (HADR) is an enterprise-class database replication feature designed to protect databases against data loss and minimize downtime. HADR replicates transactions from a primary database to a secondary, standby database.

The Log Shipping Engine

Unlike trigger-based or SQL-replication models that re-run SQL statements, DB2 HADR replicates transactions at the physical storage layer using **transaction log shipping**.

As transactions are committed on the Primary database, its log writer EDU (db2loggw) writes log records to disk. The HADR primary thread (db2hadrp) intercepts these log records and sends them over a secure TCP/IP connection to the Standby database.

On the Standby, the HADR standby process (db2hadrs) receives the logs into memory and passes them to a log replay engine, which performs continuous recovery to keep the standby database in sync.

HADR State Transitions
  • Local Catch-up: Occurs when HADR starts. The Standby database reads and replays transaction logs stored on its local disk.
  • Remote Catch-up: The Standby reads and replays logs shipped by the Primary database over the network.
  • Peer State: The Primary and Standby databases are in sync. Active transaction logs are replicated in real-time. This is the normal operating state for HADR replication.
Heartbeats and Link Monitoring

While in Peer state, both databases exchange regular network **heartbeats** to monitor connection health. If the standby fails to respond within the timeout defined by the HADR_TIMEOUT parameter, the primary marks the standby as disconnected to prevent blocking active database transactions.

2. In-Depth HADR Standby Synchronization Modes

The choice of HADR synchronization mode determines when a transaction on the primary database returns a success code to the client application. DB2 supports four sync modes:

1. SYNC (Synchronous Replication)

Mechanism: The primary writes transaction logs to its local disk and sends them to the standby. The standby receives the logs and writes them to its local disk. The primary transaction commits only AFTER receiving confirmation that the logs are secured on the standby's disk.

  • Data Loss Risk (RPO): Zero (RPO = 0). Guaranteed consistent replica.
  • Transaction Latency: High (includes network round-trip and standby I/O time).

2. NEARSYNC (Near-Synchronous Replication)

Mechanism: The primary writes logs locally and sends them to the standby. The standby receives the logs into its memory log buffer (RAM) and sends an acknowledgment to the primary. The primary commits the transaction as soon as it receives this RAM acknowledgment, without waiting for the standby to write the logs to disk.

  • Data Loss Risk (RPO): Extremely low (data loss only if both primary and standby lose power simultaneously).
  • Transaction Latency: Low (network transit time only; bypasses standby disk I/O latency).

3. ASYNC (Asynchronous Replication)

Mechanism: The primary writes transaction logs to its local disk and sends them to the local TCP/IP socket buffer. The primary commits the transaction immediately, without waiting for the standby to receive or acknowledge the logs.

  • Data Loss Risk (RPO): Moderate (potential data loss if the primary crashes before logs transit the network).
  • Transaction Latency: Very low (independent of standby performance). Ideal for replication across wide area networks (WANs).

4. SUPERASYNC (Super-Asynchronous Replication)

Mechanism: The primary database writes logs locally and commits transactions immediately. The log shipping engine runs entirely in the background, decoupled from transaction processing. The databases never enter Peer state.

  • Data Loss Risk (RPO): Highest (subject to network latency and replication lag).
  • Transaction Latency: Zero HADR overhead. Ideal for unreliable networks or long-distance disaster recovery environments.

3. HADR Database Configuration Parameters

To enable HADR, you must configure archival logging (circular logging is not supported) and set the following parameters in the Database Configuration (db cfg) file:

HADR DB CFG Configuration Script
-- 1. Enable archival logging (required for HADR)
db2 "UPDATE DB CFG FOR FINEDB USING LOGARCHMETH1 DISK:/dbdata/archive_logs"

-- 2. Configure network hosts and connection details
db2 "UPDATE DB CFG FOR FINEDB USING HADR_LOCAL_HOST 192.168.10.51"
db2 "UPDATE DB CFG FOR FINEDB USING HADR_LOCAL_SVC 50010"
db2 "UPDATE DB CFG FOR FINEDB USING HADR_REMOTE_HOST 192.168.10.52"
db2 "UPDATE DB CFG FOR FINEDB USING HADR_REMOTE_SVC 50010"
db2 "UPDATE DB CFG FOR FINEDB USING HADR_REMOTE_INST db2inst1"

-- 3. Select replication mode (SYNC, NEARSYNC, ASYNC, SUPERASYNC)
db2 "UPDATE DB CFG FOR FINEDB USING HADR_SYNCMODE NEARSYNC"

-- 4. Configure peer window timeout (seconds)
db2 "UPDATE DB CFG FOR FINEDB USING HADR_PEER_WINDOW 120"

Sizing the Peer Window (HADR_PEER_WINDOW)

The HADR_PEER_WINDOW parameter is a key setting for high availability. It defines a duration (in seconds) that the Primary database will remain in a simulated peer state if the Standby database becomes unreachable.

If the Primary crashes within this window, the Standby can perform a zero-data-loss failover safely. If this window is set to 0, any connection loss causes the primary to immediately exit peer state, increasing the risk of data loss on failover.

4. Monitoring HADR States

To inspect the health and performance of HADR replication, DBAs use the command-line utility db2pd:

Inspect HADR Health
db2pd -db FINEDB -hadr

Analyzing db2pd Output Fields

  • HADR_ROLE = PRIMARY: Indicates this database is the active primary instance.
  • HADR_STATE = PEER: Confirms that the databases are in Peer state and logs are replicating in real-time.
  • HADR_CONNECT_STATUS = CONNECTED: Confirms that the replication partner is online and communicating.
  • LOG_GAP_IN_BYTES = 0: Shows the replication lag between the primary and standby databases. A value of 0 indicates the databases are in sync.

Topic 36: HADR Implementation, Configuration & Failover Management

1. High-Level Concept & Architecture

Configuring and maintaining HADR replication is only the first part of database availability. DBAs must also manage failovers during outages and maintain data consistency.

Planned Graceful Takeover

A planned role reversal (e.g., during scheduled OS patching or database upgrades).

  • The DBA issues the TAKEOVER HADR command on the Standby.
  • The databases perform a clean swap: the current primary becomes the standby, and the standby becomes the new primary database.
  • Data Loss: Zero. All pending transaction logs are fully replayed before the role swap completes.
Unplanned Forced Takeover

Executed when the Primary database server suffers a catastrophic failure (e.g., power loss, hardware crash).

  • The DBA issues the TAKEOVER HADR ... BY FORCE command on the Standby database.
  • The Standby forces itself to become the active Primary.
  • Data Loss: Depends on the configured synchronization mode and network latency during the crash.

Understanding and Preventing Split-Brain Scenarios

What is Split-Brain? Split-brain occurs when a network partition separates the Primary and Standby databases. If both databases assume they are the active Primary and begin writing client transactions independently, their data logs diverge, causing corruption.

DB2 Protections: DB2 prevents split-brain using handshake checks when connections are restored. If a diverged standby attempts to connect, the primary rejects the handshake. To automate failover and node fencing, DB2 integrates with cluster managers like IBM Tivoli System Automation for Multiplatforms (TSAMP) or Pacemaker.

2. Step-by-Step Initialization & Failover CLP Commands

The following commands outline the full procedure to initialize, start, and failover HADR replication.

Step 1: Backup Primary Database
-- On Primary Server: Take a complete database backup
db2 "BACKUP DATABASE FINEDB TO '/dbdata/backups' COMPRESS"
Step 2: Restore Database on Standby Server
-- On Standby Server: Restore the database from the primary backup
db2 "RESTORE DATABASE FINEDB FROM '/dbdata/backups' TAKING OLDER LOGS"
Step 3: Update DB CFG Settings on Both Hosts
-- Primary Database Configuration
db2 "CONNECT TO FINEDB"
db2 "UPDATE DB CFG FOR FINEDB USING HADR_LOCAL_HOST 192.168.10.51 HADR_LOCAL_SVC 50010"
db2 "UPDATE DB CFG FOR FINEDB USING HADR_REMOTE_HOST 192.168.10.52 HADR_REMOTE_SVC 50010"
db2 "UPDATE DB CFG FOR FINEDB USING HADR_REMOTE_INST db2inst1 HADR_SYNCMODE NEARSYNC"

-- Standby Database Configuration (Execute on Standby server)
db2 "CONNECT TO FINEDB"
db2 "UPDATE DB CFG FOR FINEDB USING HADR_LOCAL_HOST 192.168.10.52 HADR_LOCAL_SVC 50010"
db2 "UPDATE DB CFG FOR FINEDB USING HADR_REMOTE_HOST 192.168.10.51 HADR_REMOTE_SVC 50010"
db2 "UPDATE DB CFG FOR FINEDB USING HADR_REMOTE_INST db2inst1 HADR_SYNCMODE NEARSYNC"
Step 4: Start HADR Operations (Always start Standby first!)
-- On Standby Host: Start as Standby (listens for incoming primary logs)
db2 "START HADR ON DATABASE FINEDB AS STANDBY"

-- On Primary Host: Start as Primary (initiates log shipping connection)
db2 "START HADR ON DATABASE FINEDB AS PRIMARY"

Technical Walkthrough: Behind the Scenes

  1. Load Shipping: When the LOAD utility runs with COPY YES on the Primary, DB2 replicates the data blocks to the Standby, keeping both tables in sync.
  2. Heartbeat Failure: Stopping the Primary instance breaks the connection. The Standby detects the failure once the HADR_TIMEOUT limit is reached.
  3. Forced Transition: Issuing the TAKEOVER HADR BY FORCE command tells the Standby to mount physical log spaces and transition to the active Primary role.
  4. Connection Handshake: When the old Primary restarts and is initialized as a Standby, it performs a connection handshake with the new Primary. The new Primary verifies the log sequences and completes the connection.

4. DBA Best Practices & Troubleshooting

Resolving Diverged Log Sequences (HADR State Sync Issues)

Diagnostic Code: SQL1767N Start HADR cannot be completed. Reason Code = "5".

Root Cause: The log sequences on the primary and standby databases have diverged (e.g., a forced takeover was executed on the standby, and transactions were written to both databases before reconnecting). The databases cannot synchronize because their histories are inconsistent.

Remedy: To resolve diverged log sequences, you must re-initialize the Standby database from a fresh backup of the Primary:

  1. Take a fresh backup of the active Primary database.
  2. Restore this backup on the Standby host, overwriting the old database.
  3. Restart HADR on the Standby: db2 "START HADR ON DB FINEDB AS STANDBY".

Connection Handshake Failure

Diagnostic Code: SQL1768N Unable to start HADR. Reason Code = "7" (Connection refused).

Root Cause: Network configuration mismatch (e.g., incorrect port assignments, remote host IP misconfigurations, or local firewalls blocking replication traffic).

Remedy: Verify that the parameters HADR_LOCAL_HOST, HADR_LOCAL_SVC, HADR_REMOTE_HOST, and HADR_REMOTE_SVC are correctly set and consistent on both servers. Also, ensure the replication ports (e.g., 50010) are open in system firewalls.

DBA Best Practices for HADR Management

  • Use a Peer Window: Always configure the HADR_PEER_WINDOW parameter (to at least 120 seconds). This allows the standby database to perform a zero-data-loss failover if the primary crashes.
  • Automate Monitoring: Write cron jobs or shell scripts that run db2pd -hadr periodically to monitor replication health and alert DBAs if a database exits PEER state.
  • Replication Port Isolation: Use dedicated network ports for HADR replication traffic to prevent bandwidth competition from standard client application connections.
