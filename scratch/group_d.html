Topic 28: DB2 Concurrency Control & Isolation Levels

1. High-Level Concept & Architecture: The Concurrency Puzzle

In a high-throughput relational database management system (RDBMS) like IBM DB2, thousands of client applications execute transactions simultaneously against the same logical tables. Concurrency control is the architectural safeguard that guarantees **Isolation** (the "I" in ACID), ensuring that concurrent operations execute safely without corrupting data or returning inconsistent, illogical results.

Defining the Three Classical ANSI SQL Read Anomalies

To design secure transaction models, a DBA must understand the exact physical data phenomena that occur when transactions run without sufficient isolation:

  • Dirty Read (Uncommitted Read): Occurs when Transaction A updates a row but does not commit. Transaction B reads this modified row. If Transaction A subsequently aborts and executes a ROLLBACK, Transaction B is left operating on "dirty", non-existent data that never formally entered the database.
  • Non-Repeatable Read (Fuzzy Read): Occurs when Transaction A reads a row. Transaction B then modifies or deletes that row and executes a COMMIT. Transaction A reads the exact same row again inside the same transaction boundary and finds that the row's values have changed, or that the row has vanished.
  • Phantom Read: Occurs when Transaction A executes a query evaluating a range predicate (e.g., retrieving all reservations for Room 101 to 200). Transaction B inserts new rows matching this range predicate and commits. Transaction A re-executes the exact same query and finds newly created "phantom" records that were not visible in the initial read.

To address these anomalies, IBM DB2 implements four distinct **Isolation Levels**, mapped directly to physical database locking mechanisms:

Uncommitted Read (UR)

Read transactions do not acquire **Share (S) locks** on rows or index pages, permitting them to read uncommitted (dirty) rows modified by active transactions. It offers maximum performance and zero read blocking. DB2 still acquires **Exclusive (X) locks** for modifying actions (inserts, updates, deletes) to protect physical data structures.

Cursor Stability (CS - Default)

Acquires an S lock on the single row at the cursor's current position. As soon as the application advances the cursor to the next row, the previous S lock is immediately released. If the application modifies the row, the lock is upgraded to an X lock and held until the transaction finishes. This prevents Dirty Reads but permits Non-Repeatable and Phantom Reads.

Read Stability (RS)

Acquires S locks on all rows that satisfy the query's criteria and holds them until the transaction executes a COMMIT or ROLLBACK. Because these locks are held, concurrent transactions cannot modify or delete the records. This prevents both Dirty and Non-Repeatable Reads, but allows Phantom Reads (as gaps are not locked, permitting inserts).

Repeatable Read (RR)

Acquires S locks on all rows scanned by the query (even if they fail the predicate check) and locks the index keys using next-key locking. These locks are held until transaction completion, preventing other applications from inserting, updating, or deleting any rows in the range. It prevents all read anomalies, but reduces concurrency and increases memory consumption.

DB2 Pessimistic Locking vs. Oracle/MySQL MVCC Architectures

  • Oracle RDBMS: Implements a pure optimistic Multi-Version Concurrency Control (MVCC) model. Read queries do not acquire locks and instead reconstruct older committed versions of rows from undo segments (rollback tablespaces). Dirty reads are architecturally impossible, and read blocking is highly rare.
  • MySQL (InnoDB): Uses MVCC via undo logs. Read transactions read a consistent snapshot of the database at a specific point in time, avoiding read locks under its Repeatable Read isolation level.
  • IBM DB2: Historically uses a strict, pessimistic locking-first architecture, leveraging the memory in the `locklist` to govern concurrencies. To match the low blockings of MVCC while retaining precise transaction states, DB2 introduced the **Currently Committed** engine feature, allowing CS reads to read the last committed transaction log state instead of blocking.

2. Full Syntax & CLP Commands

DBAs and application developers can override the active isolation level at the query level, transaction level, or terminal level using specific Command Line Processor (CLP) operations and SQL commands.

DB2 SQL Query-Level Isolation Override
-- 1. Read uncommitted data directly (Dirty read enabled)
SELECT * FROM HOTELDB.Bookings WHERE RoomNumber = 204 WITH UR;

-- 2. Force Cursor Stability (Release row locks as cursor moves)
SELECT * FROM HOTELDB.Bookings WHERE RoomNumber = 204 WITH CS;

-- 3. Lock all qualifying rows until transaction completion (Prevent updates/deletes)
SELECT * FROM HOTELDB.Bookings WHERE PriceTier = 'SUITE' WITH RS;

-- 4. Lock all scanned rows and ranges completely (Seal entire table segment)
SELECT * FROM HOTELDB.Bookings WHERE PriceTier = 'SUITE' WITH RR;
CLP Terminal and Package Binding Commands
# 1. Connect to the database and override isolation level for the active session
db2 CONNECT TO HOTELDB
db2 SET CURRENT ISOLATION = UR

# 2. Bind a DB2 package containing SQL scripts with a designated isolation level
db2 BIND my_app_package.bnd ISOLATION UR

# 3. Terminate connection to apply modifications and clean up memory
db2 TERMINATE

4. DBA Best Practices & Troubleshooting: Tuning "Currently Committed"

By default, DB2 LUW uses the **Currently Committed** behavior for Cursor Stability queries. This feature instructs the database manager to return the last committed version of a row to a read transaction if the current version is locked by a concurrent write transaction.

Advantages of Currently Committed (cur_commit)

  • Reduces lock contention and eliminates standard read-writer blockings without using uncommitted read dirty states.
  • Saves memory in the lock list by preventing active queues of waiting reader threads.
  • Does not require application-level code modifications or query overrides.

When to Disable Currently Committed

  • When processing financial ledgers or inventory bookings where the reader *must* wait for the active write transaction to determine exact balance calculations.
  • When legacy systems depend on explicit reader-writer lock queues to guarantee sequential transaction execution.
Checking and Adjusting the cur_commit Configuration
# 1. View the current setting of cur_commit
db2 GET DATABASE CONFIGURATION FOR HOTELDB | grep CUR_COMMIT

# 2. Toggle the database setting ON (Default for v9.7+)
db2 UPDATE DATABASE CONFIGURATION FOR HOTELDB USING cur_commit ON

# 3. Toggle the database setting OFF (Forces readers to block on write locks)
db2 UPDATE DATABASE CONFIGURATION FOR HOTELDB USING cur_commit OFF

# 4. Force changes to take effect by resetting connections
db2 TERMINATE
db2 DEACTIVATE DATABASE HOTELDB
db2 ACTIVATE DATABASE HOTELDB

Topic 29: DB2 Locking Architecture & Advanced Lock Modes

1. High-Level Concept & Architecture: DB2 Lock Hierarchy

IBM DB2 employs a multi-layered locking engine to balance concurrency and system resources. DB2 executes locks against physical assets in a strict hierarchy: **Database → Tablespace → Table → Row**. To access individual rows, DB2 requests intention locks at higher levels to ensure concurrent transactions do not drop the tables or modify the physical schema layout.

Demystifying Core Lock Modes

  • S (Share): The reader lock. Allows the holding transaction and concurrent users to read data, but prevents concurrent modifications.
  • X (Exclusive): The writer lock. Gives the holding transaction exclusive modification access. Blocks all other locks (S, U, X).
  • IS (Intent Share): Acquired at the table level. Indicates the transaction intends to acquire S locks on individual rows.
  • IX (Intent Exclusive): Acquired at the table level. Indicates the transaction intends to acquire X locks on individual rows.
  • U (Update): Acquired when a query intends to update a row (e.g., SELECT FOR UPDATE). A U lock is compatible with S locks, but blocks other U or X locks, preventing potential conversion deadlocks. It upgrades to an X lock when the row is modified.
  • SIX (Share with Intent Exclusive): Acquired at the table level when a transaction reads the entire table but plans to perform updates on specific rows.

Mechanics of Lock Conversion

A lock conversion occurs when a transaction already holds a lock on a resource but must transition to a stronger lock mode (e.g., upgrading an S lock to an X lock to perform an update). If two transactions hold S locks on the same row and both attempt to convert to X locks concurrently, they block each other indefinitely, resulting in a **Lock Conversion Deadlock**.

DB2 utilizes **U (Update) locks** to prevent this issue. Because only one transaction can acquire a U lock on a row at a time, it acts as a gatekeeper, preventing concurrent conversion requests and ensuring smooth serialization.

2. Full Syntax & CLP Commands

A DBA can force explicit locks on tables to run heavy batch scripts, or query DB2's real-time administrative system views to identify active locks and lock waits.

Explicit Table Locking Command
-- 1. Explicitly lock a table in Share Mode (Read allowed, updates blocked)
LOCK TABLE HOTELDB.Bookings IN SHARE MODE;

-- 2. Explicitly lock a table in Exclusive Mode (No concurrent reads/writes allowed)

3. Industry-Standard Practical Lab: Lock Upgrades & U Lock Protection

This lab simulates an upgrade operation on hotel suite accounts, demonstrating how S lock conversions cause deadlocks and how U locks protect database integrity.

Step-by-Step Dual Terminal Simulation

Part A: The Conversion Deadlock (Unsafe Upgrade Pattern)
Step 1: Terminal 1 acquires an S lock on Room 305
db2 +c "SELECT TotalPrice FROM HOTELDB.Bookings WHERE RoomNumber = 305 WITH RS"
Step 2: Terminal 2 acquires an S lock on the same room
db2 +c "SELECT TotalPrice FROM HOTELDB.Bookings WHERE RoomNumber = 305 WITH RS"

DBA Note: Since S locks are compatible, both sessions succeed.

Step 3: Terminal 1 attempts to upgrade the suite price (Converts S to X)
db2 "UPDATE HOTELDB.Bookings SET TotalPrice = TotalPrice + 50.00 WHERE RoomNumber = 305"

Expected Behavior: Terminal 1 blocks, waiting for Terminal 2 to release its S lock.

Step 4: Terminal 2 attempts to upgrade the suite price (Converts S to X)
db2 "UPDATE HOTELDB.Bookings SET TotalPrice = TotalPrice + 50.00 WHERE RoomNumber = 305"

Expected Behavior: The database engine halts. The deadlock detector discovers the cyclic wait. Within seconds, Terminal 2 is terminated as the victim: 

SQL0911N  The current transaction has been rolled back because of a deadlock 
or timeout. Reason code "2".  SQLSTATE=40001
Part B: Safe Upgrade Pattern utilizing Update (U) Locks

Ensure both sessions execute ROLLBACK before starting Part B.

Step 1: Terminal 1 requests a U lock on Room 305
db2 +c "SELECT TotalPrice FROM HOTELDB.Bookings WHERE RoomNumber = 305 FOR UPDATE"

DBA Note: Using FOR UPDATE instructs DB2 to acquire a U lock instead of an S lock.

Step 2: Terminal 2 attempts to read Room 305 with upgrade intentions
db2 +c "SELECT TotalPrice FROM HOTELDB.Bookings WHERE RoomNumber = 305 FOR UPDATE"

Expected Behavior: Terminal 2 blocks immediately. Because U locks are incompatible with other U locks, Terminal 2 must wait for Terminal 1 to complete.

Step 3: Terminal 1 executes the update safely
db2 "UPDATE HOTELDB.Bookings SET TotalPrice = TotalPrice + 50.00 WHERE RoomNumber = 305"

DBA Note: Terminal 1's U lock is successfully promoted to an X lock. Since no other S or U locks exist, it completes instantly.

Step 4: Terminal 1 commits its transaction
db2 "COMMIT"

Result: Terminal 2 is instantly unblocked, receives the updated pricing, and acquires its U lock safely without any deadlock errors.

4. DBA Best Practices & Troubleshooting: Index Optimization

Locks are managed in memory by DB2's engine. If a query does not utilize an index to find a row, the optimizer is forced to perform a **Table Scan**. During a table scan, DB2 must lock every row in the table to evaluate the predicate.

The Danger of Unindexed Table Scans

  • Drastically increases lock memory footprint, often leading to lock escalations.
  • Blocks concurrent transactions from performing operations on unrelated rows.
  • Forces S locks on every record under RS and RR isolation levels, freezing the entire table.

DBA Remedies & Index Design Rules

  • Ensure all foreign key columns are indexed to prevent share locks from climbing to parent tables during deletes.
  • Regularly execute RUNSTATS on active tables to provide the optimizer with accurate stats, ensuring it selects index scans over table scans:
    DB2 Runstats command
    db2 RUNSTATS ON TABLE HOTELDB.Bookings AND INDEXES ALL
  • Use the DB2 Design Advisor (db2advis) to suggest optimal index layouts for complex join statements.

Topic 30: DB2 Lock Administration & Configuration Tuning

1. High-Level Concept & Architecture: Memory Allocation

In IBM DB2, the allocation and governance of lock memory are defined by three critical Database Configuration (DB CFG) parameters: **LOCKLIST**, **MAXLOCKS**, and **LOCKTIMEOUT**. Understanding these parameters is essential for database stability.

Lock Memory Configuration Parameters

  • LOCKLIST: Defines the amount of database memory (allocated in **4 KB pages**) dedicated to storing row and table locks. Every lock in DB2 requires a small memory entry (roughly 128 bytes per lock). If this memory pool is exhausted, the engine must free space using **Lock Escalation**.
  • MAXLOCKS: Defines the maximum percentage of the overall LOCKLIST memory that a single transaction is allowed to consume. If a transaction's lock count exceeds this threshold, DB2 immediately triggers lock escalation on that transaction.
  • LOCKTIMEOUT: Specifies the duration (in seconds) that an application will wait to acquire a locked resource before timing out. By default, LOCKTIMEOUT is set to -1, meaning the application will **wait indefinitely**. In production, this can cause permanent application hangs and database blockages.

The Lock Escalation Phenomenon

How it works: When the LOCKLIST is full, or a single transaction exceeds its MAXLOCKS percentage, DB2 frees memory by converting multiple row-level locks on a table into a single table-level lock (e.g., converting 5,000 Row Exclusive (X) locks into one Table Exclusive (X) lock).

Why it is catastrophic: While escalation instantly frees up lock memory, it severely degrades database concurrency. An Exclusive (X) table lock prevents all concurrent transactions from accessing, reading, or modifying *any* row inside that table, causing widespread application blockage.

2. Full Syntax & CLP Commands

DBAs configure lock parameters using DB CFG utilities. These parameters are dynamic, allowing modifications to take effect without database restarts.

CLP Configuration Operations
# 1. Inspect current locking configuration parameters
db2 GET DATABASE CONFIGURATION FOR HOTELDB | grep -E "LOCKLIST|MAXLOCKS|LOCKTIMEOUT"

# 2. Update LOCKLIST memory pool to 50,000 pages (approx. 200 MB)
db2 UPDATE DATABASE CONFIGURATION FOR HOTELDB USING LOCKLIST 50000

# 3. Restrict any single transaction from consuming more than 20% of the lock list
db2 UPDATE DATABASE CONFIGURATION FOR HOTELDB USING MAXLOCKS 20

# 4. Set the lock wait timeout limit to 30 seconds (Eliminate infinite waiting)
db2 UPDATE DATABASE CONFIGURATION FOR HOTELDB USING LOCKTIMEOUT 30

# 5. Flush package cache and apply changes dynamically
db2 TERMINATE

4. DBA Best Practices & Troubleshooting: Memory Sizing & Ratios

Configuring appropriate locking limits is essential to prevent lock escalations while avoiding system memory waste.

The DBA Lock Sizing Formula

Each lock consumes approximately **128 bytes** in memory. As a best practice, size the LOCKLIST page allocation using this standard formula:

LOCKLIST (in 4 KB Pages) = (Active_Users × Average_Locks_Per_User × 128 Bytes) / 4096 Bytes

Example: For 500 active users averaging 100 row locks each:
(500 × 100 × 128) / 4096 = 1,562 pages. Adding a 50% safety margin gives a recommended configuration of **2,500 pages**.

Recommended Settings for Production Environments

  • MAXLOCKS: Set between **10% and 30%**. Setting it too high allows a single poorly written batch transaction to consume the entire lock pool, blocking all other transactions.
  • LOCKTIMEOUT: Set between **15 and 30 seconds**. Never leave it at -1 in production. Setting a timeout ensures client connections fail quickly and cleanly rather than hanging indefinitely.
  • STMM Memory Tuning: Enable automatic tuning (STMM) for locklist memory to let DB2 dynamically adjust the pool size based on active workloads:
    Enable automatic lock list tuning
    db2 UPDATE DATABASE CONFIGURATION FOR HOTELDB USING LOCKLIST AUTOMATIC MAXLOCKS AUTOMATIC

Topic 31: Advanced Locking Diagnostics & Troubleshooting

1. High-Level Concept & Architecture: Deadlock Detection

A **Deadlock** is a classic database concurrency conflict where two or more transactions are unable to proceed because each holds a lock that the other requires to continue, creating a circular dependency.

Deadlocks vs. Lock Timeouts

  • Lock Timeout (SQL0911N RC 68): An application waits for a single resource held by another user. No circular dependency exists; the waiting transaction simply times out because the holder took too long.
  • Deadlock (SQL0911N RC 2): A circular blockage (e.g., Transaction A locks Row 1, Transaction B locks Row 2. Transaction A then requests a lock on Row 2 and blocks; Transaction B requests a lock on Row 1 and blocks). Neither transaction can proceed, and they will wait indefinitely unless the database engine intervenes.

To resolve deadlocks, DB2 runs a background engine thread (EDU) called the **Deadlock Detector Daemon (db2dlock)**. The daemon performs the following actions:

  1. Wakes up at designated intervals defined by the database parameter DLCHKTIME (default: 10,000 milliseconds / 10 seconds).
  2. Scans active lock states in memory to construct a **Directed Wait-For Graph (WFG)**.
  3. Searches for loops or cyclic dependencies inside the graph structure.
  4. Selects a **Deadlock Victim** to break the cycle. DB2 chooses the victim transaction that has **written the least amount of transaction recovery logs** (minimizing rollback costs).
  5. Aborts the victim's active transaction, releases its locks, and throws error **SQL0911N Reason Code 2**, allowing the surviving transaction to complete successfully.

2. Full Syntax & CLP Commands

DBAs utilize db2pd, a non-intrusive command-line tool, to inspect lock structures directly from the engine's shared memory without the overhead of standard SQL execution.

db2pd Diagnostic Commands
# 1. Retrieve all active lock allocations for a database
db2pd -db HOTELDB -locks

# 2. Identify active lock waits (Shows waiting agents and blocking holders)
db2pd -db HOTELDB -wlocks

# 3. View detailed application information for waiting sessions
db2pd -db HOTELDB -apinfo

# 4. Combine transactions, locks, and application info into a single report
db2pd -db HOTELDB -transactions -locks -apinfo
Creating a Lock Event Monitor
-- 1. Create a table-based event monitor to track deadlock and lock timeout details
CREATE EVENT MONITOR LOCK_MONITOR FOR LOCKING WRITE TO UNFORMATTED EVENT TABLE;

-- 2. Activate the lock event monitor
SET EVENT MONITOR LOCK_MONITOR STATE 1;

3. Industry-Standard Practical Lab: The Deadlock Collision Lab

This lab simulates a circular deadlock collision between two reception clerks updating rooms in different sequences, demonstrating how DB2 resolves the conflict.

Step-by-Step Dual Terminal Simulation

Step 1: Terminal 1 locks Room 204 (Step A)
db2 +c "UPDATE HOTELDB.Bookings SET GuestName = 'Jack' WHERE RoomNumber = 204"

DBA Note: Terminal 1 holds an Exclusive (X) lock on row 204.

Step 2: Terminal 2 locks Room 305 (Step B)
db2 +c "UPDATE HOTELDB.Bookings SET GuestName = 'Jill' WHERE RoomNumber = 305"

DBA Note: Terminal 2 holds an Exclusive (X) lock on row 305.

Step 3: Terminal 1 requests a lock on Room 305 (Blocked)
db2 "UPDATE HOTELDB.Bookings SET GuestName = 'Jack' WHERE RoomNumber = 305"

Expected Behavior: Terminal 1 blocks, waiting for Terminal 2 to release its lock.

Expected Behavior: Terminal 2 blocks. A circular wait is now created between Terminal 1 and Terminal 2.

Step 5: The Deadlock Detector Daemon breaks the collision

Within 10 seconds, Terminal 2 receives a rollback error, terminating its transaction:

SQL0911N  The current transaction has been rolled back because of a deadlock 
or timeout. Reason code "2".  SQLSTATE=40001

Terminal 1 is instantly unblocked, its second update completes successfully, and it can commit its changes:

db2 "COMMIT"

Result: DB2 successfully resolved the deadlock by rolling back the transaction with the smaller log footprint (Terminal 2), allowing Terminal 1 to finish. No infinite hang occurred.

4. DBA Best Practices & Troubleshooting: Log Parsing & Deadlock Prevention

When a deadlock or lock timeout occurs, details are written to the database diagnostic log file (db2diag.log). DBAs must know how to parse these entries to identify and resolve concurrency issues.

Parsing db2diag.log for Concurrency Failures

Use the db2diag tool with targeted filter arguments to find deadlock (RC 2) and lock timeout (RC 68) records:

db2diag Filter Commands
# 1. Search for deadlock victim events in db2diag.log
db2diag -g "Reason code: 2" -level "Error, Severe"

# 2. Search for lock timeout events in db2diag.log
db2diag -g "Reason code: 68" -level "Error, Severe"

DBA Best Practices for Preventing Deadlocks

  • Enforce a Uniform Ordering of Operations: Ensure all application modules access and update tables in the exact same logical order (e.g., always update `Bookings` before `Customers`). This prevents the circular wait conditions necessary for deadlocks to occur.
  • Minimize Transaction Scope: Execute small, focused transactions. Long-running transactions hold locks longer, increasing the probability of lock timeout and deadlock conflicts.
  • Avoid User Interaction inside Transaction Boundaries: Never prompt users for input while a transaction is active and holding locks.
  • Index Foreign Key Columns: Prevents table-level share locks on child tables when rows in the parent table are deleted.
