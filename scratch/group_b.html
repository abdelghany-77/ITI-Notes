Topic 19: Database Objects - Clustered Indexes & Sequences

1. High-Level Concept & Architecture

In IBM DB2 LUW, Clustered Indexes and Sequences are specialized database objects designed to optimize storage physical access structures and concurrent numerical key generation.

The Clustering Index Model

Unlike index-organized tables (found in Oracle IOT or MySQL InnoDB where the primary key physically represents the table rows), a DB2 Clustering Index is a secondary structure. It instructs the DB2 engine to attempt to physically insert and maintain table records in the exact sorting sequence of the index keys.

When a clustering index is defined, DB2 uses space-allocation algorithms to place new inserts on the same page as existing rows with similar key values. Range scans become sequential, allowing DB2's Prefetchers (`db2pfch`) to fetch groups of data pages in a single disk sweep, reducing random disk I/O bottlenecks.

High-Performance Sequences

A Sequence is an independent schema object that generates sequential numbers according to the defined specifications. It is highly optimized for multi-client execution.

Unlike identities which are tightly coupled to a single table schema, a sequence is an independent first-class database entity. By caching generated ranges in memory (managed by Engine Dispatchable Units - EDUs), multiple applications can fetch values simultaneously using NEXT VALUE without table-level serialization locks.

Key Structural Differences: Sequences vs. Identity Columns

  • Scope: Sequences are decoupled from tables and can be shared across multiple tables, schemas, or within conditional logic. Identity columns are locked to a single table.
  • Data Manipulation: A sequence's current state can be altered dynamically (e.g. RESTART WITH) without dropping the sequence, whereas identity columns require heavy table alterations.
  • Uniqueness: Identity columns strictly guarantee that the database generates the number on insert. Sequences can be retrieved via standalone query (e.g., in application code) and inserted into non-primary key columns or custom XML paths.

2. Full Syntax & CLP Commands

Professional DBAs utilize specialized CLP statements to build tablespaces, define table clustering indexes, and fine-tune sequence caching parameters.

DB2 CLP: Tablespace, Clustering Index, and Sequence Definition
-- 1. Create a dedicated automatic storage tablespace with a 16KB page size
CREATE TABLESPACE bank_data_ts 
  PAGESIZE 16384 
  MANAGED BY AUTOMATIC STORAGE;

-- 2. Create the core Accounts table
CREATE TABLE bank.Accounts (
  AccountID BIGINT NOT NULL,
  BranchID INT NOT NULL,
  AccountType VARCHAR(15) NOT NULL,
  Balance DECIMAL(15,2) NOT NULL,
  CONSTRAINT pk_accounts PRIMARY KEY (AccountID)
) IN bank_data_ts;

-- 3. Create a Clustering Index on BranchID to group branches physically
CREATE INDEX bank.idx_accounts_branch 
  ON bank.Accounts (BranchID ASC) 
  CLUSTER;

-- 4. Create an Auditable Sequence with optimized caching
CREATE SEQUENCE bank.AccountNumberSeq
  AS BIGINT
  START WITH 100000
  INCREMENT BY 1
  MINVALUE 100000
  MAXVALUE 999999999999
  NO CYCLE
  CACHE 100
  ORDER;

-- 5. Modify existing indexing and sequence attributes
ALTER INDEX bank.idx_accounts_branch NOT CLUSTER;
ALTER INDEX bank.idx_accounts_branch CLUSTER;

ALTER SEQUENCE bank.AccountNumberSeq 
  RESTART WITH 200000 
  CACHE 250;

SQL/CLP Command Parameter Breakdown

  • CLUSTER: Tells the database engine to physically cluster all rows according to the sorting rules of this index. Only one clustering index is allowed per table.
  • AS BIGINT: Defines the underlying storage data type for the sequence values.
  • NO CYCLE: Prevents the sequence from resetting to the minimum value once it reaches the maximum value, preventing duplicate keys under a primary key constraint.
  • CACHE 100: Instructs DB2 to generate and hold 100 sequential numbers in memory. This eliminates database catalog access I/O on every sequence query, accelerating concurrent inserts.
  • ORDER: Guarantees that numbers are generated in the exact order of transaction requests (crucial for time-sensitive audit trails).

3. Industry-Standard Practical Lab

Scenario: A corporate banking institution wants to optimize performance for branch-level financial report generations. The DBA must group accounts physically by branch using a clustering index and generate account numbers using a high-performance database sequence.

DBA Lab Execution Script
-- Logged in as the DB2 Instance Owner (db2inst1)
db2 "CONNECT TO ITIDB"

-- Step 1: Create the sequence and table
db2 "CREATE TABLE bank.Accounts ( \
       AccountNo BIGINT NOT NULL PRIMARY KEY, \
       BranchID INT NOT NULL, \
       Balance DECIMAL(15,2) NOT NULL \
     )"

db2 "CREATE INDEX bank.idx_accounts_branch ON bank.Accounts (BranchID ASC) CLUSTER"

db2 "CREATE SEQUENCE bank.AccountNumberSeq AS BIGINT START WITH 500000 INCREMENT BY 1 CACHE 5"

-- Step 2: Insert banking accounts using the sequence next value
db2 "INSERT INTO bank.Accounts VALUES (NEXT VALUE FOR bank.AccountNumberSeq, 101, 75000.00)"
db2 "INSERT INTO bank.Accounts VALUES (NEXT VALUE FOR bank.AccountNumberSeq, 102, 120000.50)"
db2 "INSERT INTO bank.Accounts VALUES (NEXT VALUE FOR bank.AccountNumberSeq, 101, 3400.00)"
db2 "INSERT INTO bank.Accounts VALUES (NEXT VALUE FOR bank.AccountNumberSeq, 103, 980000.00)"
db2 "INSERT INTO bank.Accounts VALUES (NEXT VALUE FOR bank.AccountNumberSeq, 102, 15000.25)"

-- Step 3: Retrieve values and verify their physical clustering
db2 "SELECT AccountNo, BranchID, Balance FROM bank.Accounts ORDER BY BranchID"

Expected CLI Terminal Output

ACCOUNTNO            BRANCHID    BALANCE
-------------------- ----------- -----------------
              500000         101          75000.00
              500002         101           3400.00
              500001         102         120000.50
              500004         102          15000.25
              500003         103         980000.00

  5 record(s) selected.

Lab Walkthrough & Reclustering Execution

Physical Organization: During table creation and initial inserts, DB2 placed rows with BranchID = 101 physically close together. Notice that AccountNo values (which indicate the chronological order of insertion: 500000, 500001, etc.) are physically stored out-of-order in our sorted query because DB2 prioritized grouping by BranchID.

Clustering Degradation: Over time, millions of arbitrary branch insertions fill database pages, forcing DB2 to place new rows in arbitrary remote pages. This degrades the table's clustering ratio.

To restore perfect clustering and eliminate page fragmentation, the DBA runs the online table reorganization utility:

DB2 Reorg CLP Command
db2 "REORG TABLE bank.Accounts INDEX bank.idx_accounts_branch"
DB20000I  The REORG command completed successfully.

4. DBA Best Practices & Troubleshooting

Indexing & Reorg Tuning Strategies
  • Singular Choice: You can only have one clustering index per table. Choose a key that represents major range-scan queries (e.g., date columns or region IDs).
  • Write Density vs volatility: Avoid defining a clustering index on highly volatile columns (frequent UPDATEs). An update to a clustered column forces DB2 to perform expensive physical row movements across pages.
  • Automate Reorgs: Implement cron jobs checking the CLUSTERING_INDEX_REORG flag via database administrative views, triggering standard REORG TABLE when the clustering ratio drops below 80%.
High-Concurrence Sequence Caching
  • Sizing the Cache: For highly concurrent transactional OLTP systems, size the sequence cache large (e.g., CACHE 500). This keeps sequence allocations completely inside CPU register cycles.
  • Handling Gaps: If the DB2 instance encounters a hard crash (e.g., power loss), all sequence numbers cached in memory but not yet committed to rows are permanently lost, creating gaps in the number sequence.
  • Auditable Contiguity: If compliance requires contiguous, gapless numbers, define the sequence as NO CACHE and ORDER. Expect an insert performance cost as each sequence request accesses system tables directly under serialization locks.

Diagnostic Codes & Remedies

  • SQL0668N Reason Code 7 ("Operation not allowed: Table in REORG Pending State")
    Root Cause: Schema changes, data alterations, or altering a clustering index has placed the table in an unsafe, fragmented state.
    Remedy: Execute a physical reorg using: db2 "REORG TABLE bank.Accounts".
  • SQL0359N ("The range of values for the identity column or sequence is exhausted")
    Root Cause: A sequence marked as NO CYCLE has hit its defined maximum boundary (MAXVALUE).
    Remedy: Increase the sequence boundaries using ALTER SEQUENCE bank.AccountNumberSeq MAXVALUE 999999999999 or activate wrapping using ALTER SEQUENCE bank.AccountNumberSeq CYCLE.

Topic 20: Connection Security & Authentication Locations

1. High-Level Concept & Architecture

In database environments, security is defined in two stages: Authentication (verifying who is attempting to connect) and Authorization (verifying what resources they can access).

Authentication vs. Authorization

Authentication: DB2 LUW does not maintain an internal database of users and passwords. Instead, authentication is managed externally by the underlying Operating System (PAM, Local Accounts) or central directories (LDAP, Active Directory, Kerberos). The database relies on configuration settings to determine where and how credentials are validated.

Authorization: Once a user's identity is authenticated, the internal DB2 engine checks authorization tables (system catalogs like SYSCAT.DBAUTH) to enforce database privileges.

SERVER (Default Location)

All authentication validation occurs entirely on the database server machine. When a client application connects, the username and password are sent in cleartext across the network to the server host, which validates the credentials using its local operating system accounts or LDAP configuration.

SERVER_ENCRYPT

Similar to SERVER, validation occurs at the database host. However, DB2 forces the client to negotiate a Diffie-Hellman cryptographic exchange. The client encrypts the database password (and optionally the username) before transmission over the network, protecting credentials from interception.

CLIENT

The database engine trusts the client workstation's operating system to validate the identity. The server assumes the client user was verified locally and accepts connection requests without validating passwords. This represents a significant security risk and is deprecated in modern production architectures.

DATA_ENCRYPT

Extends SERVER_ENCRYPT by encrypting not only the login credentials during the handshake but also all subsequent user data, query texts, and transaction payloads transmitted between the client and database server.

2. Full Syntax & CLP Commands

Authentication configurations are managed at the global instance level inside the Database Manager Configuration (DBM CFG).

DB2 CLP: DBM Configuration for Connection Security
-- 1. Inspect the current database manager authentication configuration
db2 GET DBM CFG | grep -i authentication

-- 2. Modify authentication to enforce password encryption during transmission
db2 UPDATE DBM CFG USING AUTHENTICATION SERVER_ENCRYPT

-- 3. Modify authentication to encrypt both credentials and query data
db2 UPDATE DBM CFG USING AUTHENTICATION DATA_ENCRYPT

-- 4. Enable full secure SSL/TLS client-server communication
db2 UPDATE DBM CFG USING AUTHENTICATION SSL

-- 5. Force the DB2 engine to recycle and apply the changes
db2stop force
db2start

Administrative Recyclability Requirement

Crucial DBA Action: Any alteration to the AUTHENTICATION parameter inside the DBM CFG will not take effect dynamically. Active client applications must be disconnected, the instance stopped (db2stop force), and restarted (db2start) for the security engine to load the new authentication requirements.

3. Industry-Standard Practical Lab

Scenario: A security auditor requires a corporate bank database manager to secure the database connection mechanism. The DBA must update the instance configuration to reject cleartext credentials and enforce SERVER_ENCRYPT as the mandatory authentication standard.

DBA Lab Console Transcript

4. DBA Best Practices & Troubleshooting

Production Security Best Practices
  • Prohibit CLIENT Authentication: Never use CLIENT authentication in a production database. A malicious user with access to a client CLI can easily forge usernames and bypass database password checks.
  • Deploy SERVER_ENCRYPT or SSL: Standardize on SERVER_ENCRYPT or SSL as the baseline database manager configuration to prevent cleartext password sniffing across corporate intranets.
  • Coordinate Security Plug-Ins: When integrating DB2 with enterprise LDAP systems, ensure the database manager configuration references the correct security plugins (SRVCON_PW_PLUGIN).
Encryption Performance Impacts
  • Handshake Cost: The Diffie-Hellman exchange required by SERVER_ENCRYPT introduces a minor CPU overhead during initial client connections.
  • Mitigation Strategy: Implement application Connection Pooling. This maintains persistent open connections, avoiding frequent connection renegotiation overhead.
  • Data Encryption: While DATA_ENCRYPT secures all data in transit, encrypting all query payloads introduces notable CPU and network processing overhead. Assess network throughput before deploying system-wide.

Diagnostic Codes & Remedies

  • SQL30082N Reason Code 24 ("Security processing failed with reason: USERNAME AND/OR PASSWORD INVALID")
    Root Cause: The user provided incorrect credentials, or the server's OS user database does not exist.
    Remedy: Check the system logs on the database host (e.g., /var/log/secure or OS Event Viewer). Verify the user account is active and the password matches.
  • SQL30082N Reason Code 19 ("Security processing failed with reason: USERID DISABLED or LOCKED")
    Root Cause: The user account has been disabled or locked out by OS-level password policies (e.g., due to too many failed attempts).
    Remedy: Contact the OS administrator to unlock the system user account using command tools like passwd -u [user].
  • SQL30082N Reason Code 15 ("Security processing failed with reason: SECURITY SERVICE ERROR")
    Root Cause: DB2 failed to communicate with the external OS security services (such as PAM or LDAP).
    Remedy: Ensure the DB2 database manager process has permission to read the system user credentials (e.g., check setuid permissions on the db2ckpw binary under the DB2 install directory).

Topic 21: Administrative Authorities: SECADM vs. DBADM

1. High-Level Concept & Architecture

Modern database security relies on the principle of Separation of Duties (SoD). Historically, a Database Administrator (DBADM) possessed absolute control over database operations, security policies, and user data. Modern DB2 installations strictly bifurcate these administrative roles into SECADM and DBADM.

The SECADM (Security Administrator)

The SECADM is the database security authority. SECADM has exclusive control over:

  • Creating and managing Database Roles, Groups, and Security Policies.
  • Granting and revoking all database authorities (including DBADM itself) and object-level privileges.
  • Activating and managing Row and Column Access Control (RCAC) rules.
  • Configuring database audit systems via db2audit.

Data Privacy Rule: By design, a SECADM cannot query user table data or execute standard operational database commands (such as table index reorganizations or tablespace allocations) unless explicitly granted.

The DBADM (Database Administrator)

The DBADM manages database operations. DBADM controls:

  • Physical storage management, creating tablespaces, buffer pools, and schema schemas.
  • Executing utility tools like BACKUP, RESTORE, RUNSTATS, and REORG.
  • Tuning local database configurations (DB CFG) to optimize query performance.

Security Rule: By design, a DBADM cannot grant authorities or privileges to other users, manage database security roles, or alter the audit trails. Under compliance configurations, a DBADM is granted WITHOUT DATA ACCESS, preventing them from reading user tables directly.

Why Separate Administrative Duties?

This architectural split prevents a single superuser account from compromising both the data and the audit trails. SECADM controls security rules, while DBADM manages operations. This separation is key to meeting compliance standards such as Sarbanes-Oxley (SOX), HIPAA, and PCI-DSS.

2. Full Syntax & CLP Commands

SECADM is the only authority capable of granting or revoking administrative authorities.

DB2 CLP: Granting and Revoking SECADM & DBADM
-- 1. Grant Security Administration authority (Can only be run by a SECADM user or Instance Owner initially)
db2 "GRANT SECADM ON DATABASE TO USER sec_admin"

-- 2. Grant operational Database Administration to a user
db2 "GRANT DBADM ON DATABASE TO USER db_manager"

-- 3. Industry-Standard: Grant DBADM with strict data access restriction (Compliance Model)
db2 "GRANT DBADM WITHOUT DATA ACCESS ON DATABASE TO USER secure_dba"

-- 4. Grant DBADM with legacy access rights (Strongly discouraged in production)
db2 "GRANT DBADM WITH DATA ACCESS ON DATABASE TO USER legacy_dba"

-- 5. Revoke administrative authorities
db2 "REVOKE SECADM ON DATABASE FROM USER sec_admin"
db2 "REVOKE DBADM ON DATABASE FROM USER db_manager"

SQL Keyword Definitions

  • WITHOUT DATA ACCESS: Explicitly blocks the DBADM user from querying tables, reading view data, or running routines containing user data within the database.
  • WITH DATA ACCESS: Grants DBADM implicit authority to execute SELECT, INSERT, UPDATE, and DELETE queries on all user tables in the database.

3. Industry-Standard Practical Lab

4. DBA Best Practices & Troubleshooting

Separation of Duties Best Practices
  • Enforce WITHOUT DATA ACCESS: Standardize on WITHOUT DATA ACCESS when granting DBADM to production database administrators. Operational DBAs do not need to view actual credit card numbers or account balances to monitor disk usage or reorg tables.
  • Keep SECADM Roles Distinct: Restrict the SECADM authority to dedicated security officers. Avoid granting both SECADM and DBADM to the same system administrator.
  • Regular Authority Auditing: Periodically query the DB2 administrative catalog view SYSCAT.DBAUTH to verify which users hold administrative privileges.
Administrative Authority Review Query

Run this SQL statement to list all accounts holding system or database administrative authority:

DB2 Catalog Query
SELECT GRANTEE, GRANTEETYPE, 
       DBADMAUTH, SECADMAUTH, DATAACCESSAUTH
FROM SYSCAT.DBAUTH
WHERE DBADMAUTH = 'Y' OR SECADMAUTH = 'Y';

Diagnostic Codes & Remedies

  • SQL0552N ("Authorized ID does not have the privilege to perform operation")
    Root Cause: A DBADM account attempted to perform security operations (such as creating a role, granting privileges, or altering an audit policy) that require the SECADM authority.
    Remedy: Log in with the SECADM user account to execute security-related statements.
  • SQL0551N ("The statement failed because the authorization ID does not have the required privilege or authority to perform the operation")
    Root Cause: A DBADM granted WITHOUT DATA ACCESS attempted to execute an SQL DML statement (like SELECT, INSERT, UPDATE) on a user table.
    Remedy: If the DBA requires data access for testing, have the SECADM explicitly grant them privileges on that specific table or schema: db2 "GRANT SELECT ON TABLE bank.Accounts TO USER db_manager".

Topic 22: DB2 Privileges & Role-Based Access Control (RBAC)

1. High-Level Concept & Architecture

Authorization in DB2 is managed through a hierarchical system of Authorities, Database Privileges, and Object Privileges.

The Database Privilege Model

Database privileges grant users the authority to perform general actions within the database. These include:

  • CONNECT: Permission to connect to the database.
  • CREATETAB: Permission to create new tables.
  • BINDADD: Permission to bind new packages or compile static SQL.
  • IMPLICIT_SCHEMA: Permitted to automatically create a schema if an object is qualified with a schema name that does not exist.
Object-Level Privileges

Provide access control to specific database objects:

  • Tables & Views: SELECT, INSERT, UPDATE, DELETE, ALTER, and INDEX.
  • Sequences: USAGE (needed to retrieve sequence values via NEXT VALUE).
  • Stored Procedures & UDFs: EXECUTE.
Role-Based Access Control (RBAC)

Instead of granting privileges directly to individual users, DBAs use database Roles.

A role is a database security object that groups privileges. Roles are superior to operating system groups because they are defined inside the database engine, do not require OS intervention, and are dynamically activated during connection.

2. Full Syntax & CLP Commands

Role creation and privilege management are administered via the CLP using standard GRANT and REVOKE syntax.

DB2 CLP: Role Creation & Privilege Management
-- 1. Create a specialized database security role
CREATE ROLE BankTellers;

-- 2. Grant core database privileges to the role
GRANT CONNECT ON DATABASE TO ROLE BankTellers;

-- 3. Grant specific table-level privileges to the role
GRANT SELECT, INSERT ON TABLE bank.Accounts TO ROLE BankTellers;

-- 4. Grant access to sequence generation
GRANT USAGE ON SEQUENCE bank.AccountNumberSeq TO ROLE BankTellers;

-- 5. Assign the role to specific database users
GRANT ROLE BankTellers TO USER teller_ali;
GRANT ROLE BankTellers TO USER teller_fatima;

-- 6. Revoke access from the role
REVOKE INSERT ON TABLE bank.Accounts FROM ROLE BankTellers;

-- 7. Remove role assignments and drop the role
REVOKE ROLE BankTellers FROM USER teller_ali;
DROP ROLE BankTellers;

Understanding "WITH GRANT OPTION"

When granting privileges (e.g., GRANT SELECT ON TABLE... TO USER user1 WITH GRANT OPTION), the target user is permitted to grant those same privileges to other users. Avoid using this in secure environments to maintain control over privilege distribution.

3. Industry-Standard Practical Lab

4. DBA Best Practices & Troubleshooting

Privilege Management Best Practices
  • Apply the Principle of Least Privilege: Limit user access to the minimum set of privileges required to perform their role. Never grant database authorities (like DBADM or DATAACCESS) to general application logins.
  • Wrap Privileges in Roles: Standardize on granting privileges to database roles rather than individual users. This simplifies user onboarding and role configuration.
  • De-authorize PUBLIC: By default, DB2 grants select privileges to the special group PUBLIC on many system catalog views. Restrict public access to protect database metadata.
Dynamic Role Auditing Query

Use this administrative query to identify which roles are assigned to which users:

DB2 Catalog Query
SELECT ROLENAME, GRANTEE, GRANTEETYPE, 
       ADMINOPTION 
FROM SYSCAT.ROLEAUTH
ORDER BY ROLENAME;

Diagnostic Codes & Remedies

  • SQL0551N ("Authorization error: user does not have privilege")
    Root Cause: The user or assigned role does not hold the required object privilege (e.g., trying to run a query without SELECT, or using a sequence without USAGE).
    Remedy: Check system catalog permissions. Grant the missing privilege to the user's role: GRANT SELECT ON TABLE [table] TO ROLE [role].
  • SQL0567N ("Invalid authorization ID specified")
    Root Cause: A GRANT or REVOKE statement referenced a user or role name that does not exist in the operating system or database catalog.
    Remedy: Verify that the user exists at the operating system level (or central directory), or that the role was created using CREATE ROLE.

Topic 23: Database Auditing & Introduction to RCAC

1. High-Level Concept & Architecture

IBM DB2 LUW provides advanced security monitoring and fine-grained data access control through Database Auditing and Row and Column Access Control (RCAC).

Database Auditing (db2audit)

The DB2 audit facility runs as an independent process outside the standard database engine. It records an auditable trail of database events.

The audit system is categorized into key areas:

  • SECMAINT: Tracks security modifications (grants, revokes, role alterations).
  • CHECKING: Tracks authorization checks, recording successes and failures during query executions.
  • OBJMAINT: Tracks database structure modifications (DDL).
  • VALIDATE: Tracks user authentication events (logins, logouts).
  • EXECUTE: Records actual SQL statements executed by users (typically introduces significant system I/O overhead).
Row & Column Access Control (RCAC)

RCAC provides fine-grained access control enforced directly at the database engine level. It is superior to standard views because it filters data transparently on the base tables.

RCAC consists of two main mechanisms:

  • Row Permissions: Dynamically filters row visibility based on the session user's role or attributes (e.g., a teller can only view accounts associated with their assigned branch).
  • Column Masks: Masks sensitive column values (e.g., credit card numbers or balances) with placeholder characters unless the user holds the appropriate role or security clearance.

2. Full Syntax & CLP Commands

Auditing configuration requires system administrative authority, while RCAC policies are created and managed by the SECADM.

DB2 CLP: Auditing Setup & RCAC Declarations
-- 1. Configure global auditing categories and start the audit daemon
db2audit configure scope SECMAINT, CHECKING, VALIDATE status BOTH;
db2audit start;

-- 2. Create a targeted audit policy for financial tables
CREATE AUDIT POLICY BankAuditPolicy 
  CATEGORIES SECMAINT STATUS BOTH, CHECKING STATUS FAILURE ERROR;

-- 3. Associate the audit policy with a table
ASSOCIATE AUDIT POLICY BankAuditPolicy WITH TABLE bank.Accounts;

-- 4. Create an RCAC Row Permission (Restrict tellers to their own branch)
CREATE PERMISSION bank.restrict_teller_branch 
  ON bank.Accounts 
  FOR ROWS WHERE 
    VERIFY_ROLE_FOR_USER(SESSION_USER, 'ManagerRole') = 1 
    OR BranchID = (SELECT BranchID FROM bank.StaffMapping WHERE Username = SESSION_USER)
  ENFORCED FOR ALL ACCESS;

-- 5. Create an RCAC Column Mask (Mask balance details)
CREATE MASK bank.mask_account_balance 
  ON bank.Accounts 
  FOR COLUMN Balance RETURN 
    CASE 
      WHEN VERIFY_ROLE_FOR_USER(SESSION_USER, 'ManagerRole') = 1 THEN Balance 
      ELSE 0.00 
    END
  ENFORCED FOR ALL ACCESS;

-- 6. Activate RCAC on the table
ALTER TABLE bank.Accounts ACTIVATE ROW ACCESS CONTROL;
ALTER TABLE bank.Accounts ACTIVATE COLUMN ACCESS CONTROL;

How RCAC Modifies Query Execution

When RCAC is active, the DB2 optimizer dynamically injects the defined PERMISSION filters and MASK evaluation logic directly into the query access plan. This occurs transparently to applications, ensuring security rules are enforced regardless of how the query is written.

4. DBA Best Practices & Troubleshooting

Auditing & RCAC Best Practices
  • Limit Audit Scope: Auditing introduces disk I/O overhead. Avoid auditing the EXECUTE category in high-transaction OLTP environments. Focus auditing on CHECKING failures and SECMAINT changes.
  • Automate Log Management: Establish crontab scripts to regularly run db2audit flush and archive audit logs to a secure external storage server, preventing local disk exhaustion.
  • Evaluate RCAC Application Impact: Be aware that RCAC dynamically alters query results. If an application executes standard mathematical aggregations (e.g., SUM(Balance)), a user with masked balances will receive an incorrect sum of 0.00. Design applications to account for access control rules.
Managing RCAC Performance
  • Optimize Subqueries: If a row permission uses dynamic subqueries (e.g., querying a staff mapping table), ensure the lookup tables are small and highly indexed to prevent query performance degradation.
  • Optimize Cache: Leverage DB2's package cache to store pre-compiled access plans, reducing the parsing overhead introduced by RCAC rules.

Diagnostic Codes & Remedies

  • SQL20204N ("An audit policy cannot be associated with the specified object type")
    Root Cause: An attempt was made to associate an audit policy with a database object type that does not support direct auditing policies.
    Remedy: Audit policies can be associated with tables, views, database authorities, or roles. They cannot be associated with individual columns or sequences.
  • SQL20408N ("The action failed because of a column mask or row permission definition")
    Root Cause: A user attempted to insert or update a row with values that violate an active row permission rule.
    Remedy: Ensure the application logic validates that user inputs comply with database access control rules.
